# 微架构设计 skill

交付目标是一份值得进入 RTL 探索的微架构草稿：资源组织和关键选择有依据，预算可复算，没有已知关键矛盾。设计应覆盖主要计算、数据流、状态、存储、外部交换和数值方案；可以采用典型路径、粗调度、保守利用率及有依据的估算范围。完整逐拍调度、详细仲裁和尾部控制、全位精确回归及物理闭合留给后续实现。原始 spec 的硬预算、接口及误差门槛不变。

`SKILL.md` 定义设计方法；`references/` 保存按需使用的计算、表示和宿主协议契约。运行控制、模型调用、版本、恢复和额度归宿主。当前 harness 显式提供内容，模型提交声明，执行层运行冻结工具并回传真实结果；skill 不自行调用模型或修改输入。

复制完整 `scripts/` 目录可脱离 harness 运行，仅依赖 Python 标准库。`scripts/evaluate.py` 用 JSON 输入输出，推导工作量、容量、流量、面积、任务周期和吞吐。工具绑定声明和原文数量，但不能证明任意 Python 语义、工作覆盖或真实实现。数据变更必须重算，不能手抄派生总计。

资源计数和预算仍需包含主要计算、非矩阵处理、状态服务、装载、输出及临时存储。峰值速率不能冒充持续性能；有效速率、利用率、重叠和面积假设要解释依据与不确定性。已声明的算术、容量和端口矛盾不能用“后续验证”掩盖。

有限执行窗口、紧凑模板和数值探针用于解决具体疑问，属于可选证据。缺少 full-lane、完整尾部或探针不自动拒绝草稿；未检查仍明确标为未检查，不能称为通过。选择精确工具时遵守其契约，不扩大局部通过的证明范围。

需求和工作模型保持原始输入、数量单位、范围和依赖可追溯。数值方案应避免已知的未定义关键路径或相互矛盾的编码；端到端误差验证仍是后续义务。独立审阅判断结构方案是否需要大改，不能由局部工具通过或提示词完整度代替。
