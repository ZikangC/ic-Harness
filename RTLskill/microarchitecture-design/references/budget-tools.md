# Declarative budget contract

The model declares work, resources and scheduling choices. The script owns deterministic formulas and all derived totals. It cannot discover omitted work, prove requirement semantics, complete scheduling or physical closure. No legacy derived-input conversion is supported.

## Execution and identity

Standalone: `python3 scripts/evaluate.py < request.json`, where the request is `{document,sources:{"spec.md":...,"reference.py":...}}`. `--require-document` also checks for substantive architecture_md. Copy the complete script bundle, including source_quantities.py, budget_units.py and abi_geometry.py; it uses Python standard library only. Inspect JSON ok/errors/gate, not process exit zero.

For a quantity catalogue/view without a design, use `python3 scripts/evaluate.py --source-quantities-only` with `{sources:{"spec.md":...,"reference.py":...}}`. The result contains content-bound token locations and a compact selector view; it extracts lexical quantities, not requirements. Extraction materialization keeps the raw declaration, canonical requirements and binding receipts separate. Raw source/convert rows never contain program-produced values or converted_from fields.

### Current harness response protocol

The following markers and repair operations are caller conventions, not microarchitecture design choices. Standalone scripts consume tool data without these envelopes and do not require a controller. Return exactly `<<<BUDGET_REQUEST>>>` followed by one JSON object `{ "tool":"evaluate_design", "document":{...} }`; its outer keys are exactly tool and document. Put candidates, selected and any corrected work_model/work_model_revision inside document, never beside it. A work_model_revision is `{reason,references:[original_input_refs]}`, using the work-model source-span contract; basis/citations are not its field names. Omit requirements (host injects the frozen extraction), architecture_md and receipts. Only text protocol, never native tools/XML. A real result arrives next turn. The host may repair serialization of one complete JSON frame through a separately charged evidence call, preserving every key/value/order/nesting. It never fills truncated content or edits Markdown; failed protocol/declaration checks remain your correction task. Inspect classified feedback alongside the original check result: schema/expression/source errors, concrete resource contradictions and valid hard-budget failures have different implications.

Final response is `<<<ARCHITECTURE_DATA>>>` with only `{ "evaluated_design_sha256":"actual last result hash" }`, followed by `<<<ARCHITECTURE_MD>>>` and the complete unified Markdown document. The hash must name the most recently executed result's actual design_sha256; any data change needs another calculation request. The host recomputes the final gate and adds the authoritative budget tables before independent audit; drafts, audit and export use the same complete text.

## Source-backed work model

The design starts with the source-only work-model entry described in [work-model.md](work-model.md). It is checked before candidates and supplied as a versioned interpretation. Its executed compact_summary reports declared active work by profile/unit/category; use actual returned IDs/totals without treating the summary as semantic proof or new formula variables. Omit an unchanged work_model. A correction supplies its complete replacement and work_model_revision under the applicable request envelope above or below, then recalculates the complete candidate set.

## Candidate declarations

Document: `{candidates:[two to four candidate objects],selected:"actual candidate id",selection_conditions:[],revision_response:[],requirement_corrections:[]}`. This host requires selected to name a real candidate, including in an explicitly unaccepted failed-search report; never use null or a prose comparison rule. Selection remains provisional if budgets fail. Each candidate contains id, organization, assumptions, calculations, macros, metrics, workloads, resource_checks, abi_fields, all five ledger arrays below, storage_phases, coverage and risks. Empty risks/calculations are legal. Empty ledgers require an explicit not_applicable basis. No top-level facts object.

Collection types are mandatory: assumptions and calculations are arrays of named row objects, never dictionaries keyed by parameter or null. macros, workloads, resource_checks, abi_fields and all five ledgers are arrays; metrics and coverage are objects (metrics={} is valid only when every constraint is automatic). The minimal container shape is:

```json
{"id":"candidate_id","organization":"resource organization","assumptions":[],"calculations":[],"macros":[],"metrics":{},"workloads":[],"resource_checks":[],"abi_fields":[],"cost_groups":[],"traffic":[],"buffers":[],"storage_phases":[],"schedule_windows":[],"area_components":[],"coverage":{},"risks":[]}
```

Populate the arrays and coverage according to the rows below; this shape is not a complete valid design. For each nonautomatic constraint use its exact supplied id in metrics, including an implementation-unverified clock entry `{status:"unverified",reason:"physical timing not measured"}`. Do not invent differently named metric keys.

Numeric fields accept literal design choices or safe expressions over frozen materialized fact identifiers and this candidate's earlier assumptions/calculations. Source numbers enter through the quantity binding and explicit conversion forms in [requirements-contract.md](requirements-contract.md); do not recopy them as candidate assumptions. Convert input quantities to compatible scales before combining them. Arithmetic `+ - * / // % **` and ceil/floor/min/max/abs only; no Python code. Named candidate rows remain `{id,value:number or expression OR formula:expression,unit,basis}` with exactly one expression. Names are unique, no input overwrite or cross-candidate references. Use these rows for reusable primitive choices or specialized calculations, not duplicate aggregate totals. Reserved macro_bits is not an input identifier.

- macros: `{name,kind:SRAM|ROM,count,depth,width,ports_and_schedule}`. Actual physical instances, positive integer dimensions, subject to extracted storage rules. Script derives total bits from sum(count*depth*width).
- cost_groups: the ONLY work-to-resource/cost declaration, `{id,workload,work_ids:active_source_work_ids_or_exact_selector,resources:[declared_macro_or_resource_check_or_area_component_ids],model,basis}`. Every active work/profile pair occurs in exactly one group; a group can cover many work items and resources can be shared by different groups. Empty work_ids are legal only for explicit additional setup/stall/output costs with a basis. There is no reverse per-work mapping. Program outputs work_trace and binding evidence from these declarations. work_ids is either an explicit unique ID array or a nonempty selector object exactly {unit:string,exclude?:[IDs]} or {category:string,exclude?:[IDs]}; never both selector keys. A selector matches only active items in this group's current profile with the exact declared operation unit or category, then removes explicitly named matched IDs. Unknown/unmatched exclusions, duplicate exclusions and an empty result are errors. No name matching, unit aliases, resource inference or implicit "remaining work" selection. Category selection does not make mixed operation units commensurate. Inspect the returned expanded IDs; the executed binding is tied to this work-model version.
  - `model:"compute"` adds `{units,operations_per_unit_cycle,overhead_cycles}`. Default `realization:"direct"` derives operations=sum(full-task source counts), requiring commensurate counted operation units. Nonarithmetic state/movement/control may be covered by the same group with a realization basis. The script derives compute_minimum_cycles=ceil(operations/(units*rate)). Optional operand_service below derives a separate service_minimum_cycles; minimum_cycles=max(compute_minimum_cycles,service_minimum_cycles), and scheduled_cycles=minimum_cycles+overhead_cycles. Without a service relation, the compute-only bound is retained and the missing relation is disclosed in evidence_gaps. The rate may be an explained effective rate with conservative utilization; overhead may use a justified coarse estimate or bound for stalls and nonarithmetic work. State whether zero overhead is an ideal lower bound or costs are covered elsewhere. Do not present peak rate as sustained throughput. These formulas are not latency proof.
  - Optional compute `operand_service:[{resource_check,operations_per_batch,operands:[{role,distinct_values,element_bits}],transfer_bits?,basis}]` binds actual different operand values to an existing resource_checks service. Each selected resource appears once in this group and must be in its resources list. operations_per_batch is a positive integer number of this group's operations. For each distinct named role, distinct_values is a nonnegative integer and element_bits is positive; use actual packed representation and reuse/broadcast, rather than assuming lanes*bits. Program derives payload_bits_per_batch=sum(distinct_values*element_bits). Optional transfer_bits is the actual service word quantum: charged_bits_per_batch=ceil(payload_bits_per_batch/transfer_bits)*transfer_bits; without it the declared model is a continuous tightly packed bitstream. Packing across roles must match the selected representation. Batches=ceil(whole_task_operations/operations_per_batch), charging the final partial batch in full, and demand_bits=batches*charged_bits_per_batch. Per-resource minimum_cycles=ceil(demand_bits/service_bits_per_cycle); separate resources overlap as a necessary bound, so the group service minimum is their maximum. Reports preserve compute/service bounds separately. Heterogeneous access patterns need an explained conservative batch model or separate accounting groups; this does not imply separate hardware engines. Capability, batch/value mapping, initial retention, reuse, bank distribution and whether the bound is schedulable remain engineering obligations; zero new values does not prove that retained values are valid or free to initialize.
  - `realization:"transformed"` adds a count recipe and equivalence covering the ENTIRE group. It may combine transformed and unchanged work, fusion or changed internal precision. The recipe counts actual implemented operations over the whole profile; it is not multiplied again by source repetitions. The script checks arithmetic, not equivalence. Split different operation units into groups unless an explicit transformed recipe and unit represents the complete implementation cost.
  - `model:"cycles"` adds cycles for complete-task nonarithmetic work only. Counted arithmetic cannot bypass resource counting through a free cycles field. Source work already realized by a compute group is not mapped again to its overhead group.
  - `model:"unsupported"` adds cycles and reason; the estimate stays explicit and gate unknown. Unsupported/unresolved source work also blocks release as unknown, never proves hardware impossibility. Do not submit operations, minimum_cycles or scheduled_cycles in any group.
- traffic: common fields `{id,model,payload_bytes,transfers,alignment_bytes,transaction_bytes,basis}`. transfers repeats an ENTIRE independently aligned payload, not its beat count. Script derives padded_bytes=ceil(payload/alignment)*alignment, total_bytes=padded_bytes*transfers, transactions=ceil(padded_bytes/transaction_bytes)*transfers, wire_bytes=transactions*transaction_bytes. Model `continuous_reserved` additionally declares latency_cycles, transactions_per_cycle, inflight, response_buffer_bytes. Script derives ceil(latency*rate) minimum credits and inflight*transaction_bytes reservation. A smaller sustained rate can use fewer credits, but the full schedule must be recosted and justified. Returned service_cycles_lower_bound=max(ceil(transactions/rate),latency) is ONLY a necessary bound. Model `posted_write` has no read-response fields; its explicit service relation below derives acceptance/drain lower bounds against actual charged cycles. Model `unsupported` requires reason; traffic is still calculated but selected gate is unknown. Streaming response consumption, variable transactions and bank/burst dependencies are not proved by these models. Do not misrepresent them to obtain pass.
  - Optional `service:{resource_check,boundary:"run"|"preloaded_before_run",basis,cost_group?,operand_relation?}` links this row's **actual wire_bytes**, including repeated aligned payloads and beat tails, to an existing service. For run, cost_group must name an actual group using that resource, and optional traffic.workload must agree with the group's profile. Program checks the charged interval >= max(ceil(wire_bytes*8/service_bits_per_cycle),existing read-request service lower bound). Ordinary serial/parallel/overlap groups must cover that bound in their own scheduled_cycles; they cannot borrow another group's spare cycles. For a group explicitly charged by an execution component, the validated template's actual charged component duration is used instead of treating the group's smaller resource lower bound as its full charge. Multiple run traffic rows using the same group/resource add their actual demand. If the same group/resource also has operand_service, explicitly set operand_relation to same_stream or independent and explain ownership in basis. Omission is an ambiguous declaration error. same_stream counts the maximum of that operand projection and all same-stream traffic; independent traffic adds to it. Without an operand projection, omit operand_relation. This relationship is an audited value/flow claim, not automatically established by equal byte counts. A preloaded_before_run relation omits cost_group and operand_relation: the tool keeps bytes and initialization minimum_cycles visible outside RUN instead of treating them as zero. This label is a design accounting claim; independent original-spec review decides whether preload before the measured boundary and reuse across runs are permitted. It cannot waive an original initialization obligation. Missing relations are recorded as unchecked, never silently validated.
- buffers and storage_phases: declare object shapes/element widths/copies/padding/metadata and live phases using [storage-tools.md](storage-tools.md). Required demand and maximum live demand are program outputs, never hand-entered required_bits. Runtime parameter domains are frozen source extraction, while representation and phases are candidate decisions. Macro aliases are checked by simultaneous demand, not by adding allocated views.
- schedule_windows: optional physical-request/operand witnesses using [execution-tools.md](execution-tools.md); the array can be empty with its existing coverage basis. Macro dimensions and port/latency service come from actual inventory and source-defined capabilities. The program checks submitted windows and permits legal packed-word/broadcast uses; it does not prove the whole repeated/tail schedule. Detailed schedule evidence is not mandatory for every compute group. Coarse resource_checks and explained rate/overhead assumptions still need to support the main budget. Old aggregate accesses/ports/accesses_per_port_cycle rows remain rejected.
- area_components: logic rows `{id,kind:"logic",count,unit_area_lower,unit_area_upper,source,uncertainty,basis,covers_buffers:[register_buffer_ids]}`. Unit costs are mm2; assumptions are uncalibrated, never measurements. When input storage_area_model is supplied, ALL macro costs come automatically from actual inventory/density: omit macro cost rows. When input model is unspecified, each macro needs one `{id,kind:"macro",resource_reference,unit_area_lower,unit_area_upper,source,uncertainty,basis}` row; count comes from inventory, omit it. Script derives lower/upper total area and uses upper for constraints. No empty area inventory or free register storage.
- coverage: `{cost_groups:{status:covered|not_applicable,basis},traffic:...,buffers:...,schedule_windows:...,area_components:...}` matching populated/empty arrays. If all costs are input-defined macros, area_components can be empty with that basis. Coverage is a declaration, not completeness proof.
- workloads: `{id,clock_fact,components:[{id,references:[cost_group_ids],composition:serial|parallel|overlap|execution,basis}]}`. Quantity comes ONLY from work_model; do not repeat items/quantity/unit. Every group for this profile appears in exactly one component; all costs are whole-task, never single-token costs. Components are consecutive nonoverlapped critical-path intervals. `serial` derives the sum of referenced costs; `parallel` derives max and requires disjoint declared resources plus a source dependency/supply explanation. `overlap` additionally supplies cycles>=max(group costs) and an explained coarse dependency/resource/port basis; the bound alone does not prove legal overlap. Include all work, initialization, movement, arbitration and output/completion in groups. clock_fact names a cited input frequency fact; the tool converts its units to Hz. The program derives task_cycles=sum(component cycles), cycles_per_item=task_cycles/quantity, items_per_second=clock_hz*quantity/task_cycles. No copied totals or reverse group-to-component links.
- An optional `execution` workload component adds `execution:{template:"actual id",component:"whole"|"actual phase id",repetitions?:expression}` and omits cycles. Its references must equal the chosen phase cost_groups, or their union for whole. The program derives inclusive duration from declared phases, then charges it once. For each referenced compute group, whole-task operations / executed active-lane operations must be the same positive integer; this derives repetitions. One lane issue is one operation in that group's declared unit. Jointly repeated phases need the same source scope; different scopes may need separate accounting groups, while hardware retains the same resource IDs. Optional repetitions must agree with the computed ratio; a nonarithmetic-only path requires it explicitly with source/traffic basis. The derived total must meet each group resource/service lower bound. Include overhead once, not both in template duration and again as added compute cost. Each charged phase is used at most once. A template used only as an optional witness may remain unpriced in evidence_gaps; once a template is used for execution pricing, its declared phases cannot be partly omitted from the budget, even if its readiness evidence remains unverified. The tool does not prove source scope, indices, producer semantics, arbitration or physical II. Retained values name actual register buffers with capacity/area accounting. Ordinary serial/parallel/overlap estimates remain available without templates. No hand-entered replacement of derived template totals is accepted.
- metrics: ONLY constraints whose quantity is not area/capacity/task_cycles/cycles_per_item/items_per_second. For these five built-in quantities script derives metrics from actual inventory, upper area and the linked workload and converts supported units. Do not provide their metric keys. Other metrics are expressions or `{status:"unverified",reason}`; implementation-unverified clock/numerical/protocol evidence must remain explicit. Never use unverified to defer a calculable hard budget.
- resource_checks: `{id,demand_per_cycle,supply_per_cycle,unit,basis}` for concrete limiting resource service, not an easy unrelated resource. Script compares same-unit declarations; it cannot prove supply is real. A selected traffic/operand service requires a positive finite supply and an explicit unit bit/cycle, bits/cycle, b/cycle, byte/cycle, bytes/cycle or B/cycle (plural cycles is accepted). Bytes convert to bits; other units are rejected for these links instead of guessed. Express prefixed source quantities through prior explicit conversion and use compatible base-unit expressions. Explain how real width, allowed ports, bank distribution, arbitration, initiation interval and any conservative utilization establish this capability.
- Linked service is also checked in each existing workload component. Demands bound to the same service across different charged groups add; independent service IDs each impose their own bound, rather than being forced serial. The component's charged duration must cover both each aggregate demand/capacity bound and the individual service minimums, including read request-rate and latency bounds, in all compositions. Operand and traffic declarations within the same group require explicit ownership when they use the same service. The program charges max(operand_demand,same_stream_traffic_demand)+independent_traffic_demand, with no silent same-stream credit. The relation's truth remains independent review; equal sizes alone do not establish identical values or transfers. These arithmetic links do not establish bank-conflict freedom, actual shared-bus identity, dependency-ready overlap or completion semantics.
- abi_fields: `{name,width,offset,carrier_width,carrier}` for actual physical words. Script checks fit and same-carrier overlap. Command meaning and discriminators remain explicit in the unified RTL contract.
- abi_geometry: fixed integer array/address recipes executed by `scripts/abi_geometry.py` inside this same calculation request. Geometry IDs, field IDs and probe IDs are identifiers. Numeric fields use existing safe expressions; lengths/alignment/beat sizes are bytes, element/carrier widths are bits and dimensions/indices are counts. Successful results publish `<geometry_id>__<result>` after assumptions/calculations, before cost/traffic ledgers; later geometry rows and traffic can use them. Existing names cannot be overwritten. Geometry data is optional for diagnosing older proposals; a new design should derive its applicable layout with these recipes and reference the outputs in its traffic and document, rather than independently handwriting offsets and wire totals. Other mappings are not proved by these recipes.
  - `region`: `{id,kind:"region",fields:[{id,payload_bytes,alignment_bytes}],beat_bytes}`. Ordered fields start relative to the region base; each offset is aligned from the previous end. Absolute field alignment also requires a compatible chosen base, which is not inferred by this relative-offset recipe. Results include `f_<field_id>__offset_bytes/end_bytes/payload_bytes/padding_before_bytes`, `payload_bytes`, `extent_bytes`, `contiguous_wire_bytes`, `contiguous_beats`, `field_beats_lower_bound` and `field_wire_bytes_lower_bound`. Payload sums valid fields; extent includes internal gaps. Contiguous wire covers the complete extent. The union of field-covering beats is only a necessary lower bound: legal skip-padding reads need their own address/service schedule. Do not force all gaps to be transferred or equate valid payload with extent.
  - `axis_pack`: `{id,kind:"axis_pack",shape:[...],axis,element_bits,carrier_bits,probes:[...]}`. The declared axis packs whole elements into byte-sized carriers; supported order is C-order with low-bit-first slots (`order:"C"`, `slot_order:"lsb_first"`). A forward probe is `{id,logical_index:[...]}`; an inverse probe is `{id,packed_index:[...],lane}`. Results include `slots_per_carrier`, `packed_axis_extent`, `carrier_count`, `packed_bytes`, `padding_bits_per_carrier`; probes publish `p_<probe_id>__carrier_index/carrier_byte_offset/element_bit_offset/logical_axis_index/packed_axis_index/lane/logical_<axis>/packed_<axis>`. Out-of-range and padding-slot probes are rejected. Explicitly name logical versus packed indices in the contract; the tool never guesses a variable's meaning.
  - `beat_span`: `{id,kind:"beat_span",payload_bytes,beat_bytes,probes:[{id,byte_offset,size_bytes}]}`. Results include `full_beat_extent_bytes`, `beats`, `tail_padding_bytes`, `last_valid_bytes`; probes publish `p_<probe_id>__aligned_byte_offset/byte_lane/first_beat/last_beat/spanned_beats`. A probe must be within valid payload. Full-beat reads need allocation covering the returned extent; masked writes require their actual byte enables and allocated bounds to be assessed separately. Check legal runtime tails, not just a divisible benchmark size.
  - Each recipe may carry basis/references. Results remain declared integer geometry and finite witnesses, not directory completeness, semantic equivalence, an executed transfer schedule or RTL proof. Unsupported order/packing is reported explicitly. The final document must quote the current outputs and explain the selected allocation/read policy; changing the declaration requires recalculation.

Do not submit area_totals, traffic.total_bytes, buffers.required_bits/allocated_bits, cost_groups.operations/compute_minimum_cycles/service_minimum_cycles/operand_service_bounds/minimum_cycles/scheduled_cycles, workload.clock_hz/task_cycles/cycles_per_item/items_per_second, built-in metric values or macro_bits calculations. They are program outputs. Omit erroneous fields from complete candidate replacements; do not set null or introduce alternate totals. Read returned ledger/workload/check results for Markdown; do not independently recompute rounded budgets in prose.

## Apply the links to the decisive budget

A new draft should execute these relations for the operand supply and external transfers that determine its selected budget, and quote the current results. An unrelated passing resource check is not evidence for a main cost group. Coarse phases, supported conservative rates and explained margins are legitimate; a complete per-cycle template is not required. A missing optional relation reports an evidence gap, while an executed contradiction is an error requiring correction. Neither absence nor a passing lower bound proves feasibility.

For example, a compute group may declare `operand_service:[{"resource_check":"packed_port","operations_per_batch":32,"transfer_bits":128,"operands":[{"role":"coefficient","distinct_values":32,"element_bits":4},{"role":"broadcast_input","distinct_values":1,"element_bits":8}],"basis":"32 operations reuse one input; selected packed word layout"}]`. This costs the stated distinct values, including service-word padding; it does not prescribe that organization. A posted output row may declare `service:{"resource_check":"external_bus","cost_group":"output","boundary":"run","basis":"accepted output writes through the completion boundary"}`. The named resource checks and charged groups must actually exist, and their capacities need original-interface or implementation-choice evidence.

## Concrete numeric boundary probes

Candidate `numeric_probes` is optional evidence in the calculation request; [numeric-tools.md](numeric-tools.md) defines scalar and output-row encoding operations, rounding/overflow policies and assertions. Empty arrays are `not_checked`; rows without assertions are `computed_only`, with pass:null. Neither is a numerical pass, but missing optional probes alone does not reject an architecture draft. Executed failed assertions or invalid declarations still require correction; passing points do not establish risk coverage or end-to-end accuracy. Critical undefined or contradictory numerical mechanisms remain engineering findings. Probe values stay scoped to numerical computation, never silently become budget assumptions. New probes require a new executed receipt.

## Small expression examples

These illustrate syntax, not project values or a recommended organization. Substitute actual workload/work/resource IDs and design choices. A MAC and a comparison are distinct units, so direct groups can share one declared ALU resource while remaining serial:

```json
{"cost_groups":[
  {"id":"g_mac","model":"compute","workload":"profile_id","work_ids":["source_mac_id"],"resources":["alu_logic_id"],"units":1,"operations_per_unit_cycle":1,"overhead_cycles":2,"basis":"whole-task MAC sequence and pipeline fill"},
  {"id":"g_compare","model":"compute","workload":"profile_id","work_ids":["source_compare_id"],"resources":["alu_logic_id"],"units":1,"operations_per_unit_cycle":1,"overhead_cycles":0,"basis":"whole-task comparisons on shared ALU"},
  {"id":"g_load","model":"cycles","workload":"profile_id","work_ids":["source_input_id"],"resources":["controller_logic_id"],"cycles":13,"basis":"concrete complete-task input schedule"},
  {"id":"g_store","model":"cycles","workload":"profile_id","work_ids":["source_output_id","source_done_id"],"resources":["controller_logic_id"],"cycles":10,"basis":"concrete complete-task output/completion schedule"}
],"workloads":[{"id":"profile_id","clock_fact":"input_clock_id","components":[{"id":"full_run","references":["g_load","g_mac","g_compare","g_store"],"composition":"serial","basis":"input, MACs, comparisons, output/completion execute consecutively"}]}]}
```

A transformed group adds EXACTLY `realization`, `equivalence` and `count` (not count_recipe/formula at group level). Example count: `{"kind":"custom","operations":"input_fact_id*2","unit":"MAC","basis":"traceable whole-task implementation count"}`. No implicit work-id-to-operation symbols exist. A transformation declaration cannot substitute for correcting an erroneous source work model. No cost or count recipes use assignments/loops or invented variables.

ABI carrier identifies one declared word FORMAT, including its discriminator/command case. Mutually exclusive formats use distinct identities such as cmd[CFG_LOW] and cmd[RUN]; all still respect the physical port width. Fields simultaneously present in a declared format share that carrier and cannot overlap. If freezing those fields in this draft, explain their actual discriminator and transport; a different carrier label alone does not prove exclusive decoding. Original externally fixed fields remain requirements. Unchosen internal bit placement can remain RTL exploration detail when capacity, addressing bounds and external semantics do not depend on it.



## Input model

Requirements include storage_area_model=`{status:"supplied",density_fact:"literal fact id"}` or `{status:"unspecified",reason}`. Density citation gives number, storage/area units and prefix basis exactly. The program normalizes explicit unit vocabulary and binds actual macro inventory to the supplied density. Unsupported supplied models must be disclosed; unspecified cannot replace a present requirement. Partial dimensional checks do not prove source meaning.

## Repair and gate

After a real result return `<<<BUDGET_REQUEST>>>` followed by one object:

```json
{"tool":"replace_candidates","base_design_sha256":"actual last hash","candidates":[{"id":"existing_candidate_id","organization":"...","assumptions":[],"calculations":[],"macros":[],"metrics":{},"workloads":[],"resource_checks":[],"abi_fields":[],"cost_groups":[],"traffic":[],"buffers":[],"storage_phases":[],"schedule_windows":[],"area_components":[],"coverage":{},"risks":[]}]}
```

The example shows the container only; populate every required declaration. Each submitted candidate must be complete and name a unique EXISTING ID. It replaces the entire candidate row, not just supplied fields; omitted wrong fields disappear. Unsubmitted sibling candidate data remains unchanged. No deep merge, rename, candidate deletion or automatic completion. The base hash must match the actual current evaluated full document, either from this session or a caller-supplied revalidated revision_base. Optional top-level selected, selection_conditions, revision_response, requirement_corrections, work_model and work_model_revision are replacement fields of this replace_candidates envelope, replacing complete values; omitted fields remain. With that current base available, candidates=[] is valid when changing only those complete optional fields, including a corrected work_model with work_model_revision reason/references. Without a revalidated base, the first request must be a complete evaluate_design document. Frozen requirements, architecture_md and receipts cannot be replaced. Every request recomputes and fingerprints the resulting full 2–4 candidate document under the same hard gate, including when candidates=[] preserves all candidate rows. To add or remove candidates, submit a full evaluate_design document. No partial-candidate acceptance or additional calculation allowance is implied.

ok=false means data/inconsistency errors: repair before final Markdown. A valid over-budget result can support an explicitly unaccepted failed-search report. gate pass means declared checks only; fail means inconsistency or selected hard overrun; unknown means an uncomputed hard budget, material unknown source work or selected unsupported cost/traffic/storage model and blocks release without claiming hardware impossibility. Optional finite-window/full-lane/template or numeric-check omissions remain in ledger.evidence_gaps; they do not independently make the architecture infeasible or establish a pass for their unperformed checks. Explain estimate assumptions and later implementation obligations. Stop at host limits. Optional optimization never requires another cycle. The host cannot silently repair design declarations.
