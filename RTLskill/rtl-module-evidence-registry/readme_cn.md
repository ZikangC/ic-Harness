# RTL 模块状态与证据登记簿

## 目的

这个 Skill 为端到端 RTL/EDA（电子设计自动化）流程维护一份可重建、可核验的模块登记簿。它回答的不是“历史日志里曾经说过什么”，而是：当前项目有哪些模块、每个模块现在是否以黑盒或 RTL body（真实 RTL 实现）参与各测量分区、是否曾经完成过有效展开验证、最近一次尝试是什么状态，以及有哪些可比较的面积和时序证据。

登记簿拆成三类持久化数据：当前快照、只追加的状态事件、只追加的测量记录。controller（控制器）每个指导周期在 Pro 决策前和执行结果后都必须重建热视图，模型只读取这个小而新的窗口。

## 必要性讨论

长期运行的大模型很难只靠提示稳定完成这件事。模块状态散落在 `ppa.toml`、filelist、RTL、不同 run 的 `result.json`、反馈和进度叙述中；旧日志中的“待展开”可能已经被后续配置推翻，退出码成功也可能没有真实 timing path（时序路径）。当输入历史不断增长时，模型还容易把“曾经验证过”和“当前已经集成”混为一谈。

真实项目已经出现过从历史叙述推测展开目标、继而选择了当前并非黑盒的模块；也出现过模块曾成功展开，但最新测量超时后旧状态文件仍指向另一个目标。继续给 Pro 增加提示只能降低概率，不能形成硬约束。登记簿把这些事实变成确定性状态，并由 controller 在动作前校验。

## 它如何工作

项目 adapter（适配层）在当前周期收集：

- filelist、RTL 扫描和当前分区配置得到的全部模块；仅在配置出现但没有可用 RTL body 的模块也必须登记，并禁止直接展开；
- 当前分区配置及每个模块的 `blackbox`、`rtl_body` 或 `not_in_scope` 表示；
- 配置、filelist、RTL 的指纹；
- 不可变结构化结果中的展开验证证据；
- 带来源、工具、库、范围和可比性键的面积/时序测量；
- 当前集成主线的结构化事件或投影；项目可选地从外部 Transaction Ledger 提供，但经 reconcile（重建）后 Registry 中带 generation 的投影是本 Skill 消费者的唯一真源。
- 由项目侧独立 extractor（提取器）构建的设计上下文：模块层次关系、源码归属、时钟/复位与边界事实，以及可选的语义意图。

`registry_gate.py reconcile` 根据来源优先级合并这些事实，输出当前 registry（登记簿）、紧凑 hot view（热视图）、新增事件和新增测量。`can-expand` 在修改黑盒配置前再次检查目标确实是当前指定分区的黑盒。`hot-view` 检查 session、cycle、phase、输入指纹和证据水位是否与当前请求一致，任何陈旧或冲突都会返回硬门 `hold`。

设计上下文不是由登记簿解析 RTL 构建的。项目侧 extractor 负责一次构建并在 RTL、filelist 或配置指纹变化后刷新；登记簿只维护其 generation（代次）、图指纹和每个模块的紧凑投影。`module-context` 查询只在上下文与当前源指纹一致时返回模块的上下游关系、时序边界和语义意图，否则返回 `hold`。这样最小 STA Skill 可以同时获得真实 diff 和当前耦合关系，而不会从文件名或旧历史猜测。

若存在 `measurement_incomplete` 或 `pending_reverify` 模块，却没有对应的 Registry 主线投影，或主线引用了与当前配置不一致的模块，登记簿会判定冲突并返回 `hold`。首次迁移时项目 adapter 只能从当前配置、结构化 result 和已持久化 Registry 恢复真实待验证模块，不能跳到下一个黑盒，也不能从 progress 叙述猜测。

关键派生状态包括：

- `integrated_verified`：当前使用 RTL body，且最新有效证据完成展开验证；
- `measurement_incomplete`：当前已使用 RTL body，但最新验证测量因预算或截断未完成；
- `temporarily_blackboxed`：历史验证仍有效，但当前策略又将其黑盒化；
- `pending_reverify`：曾验证过，但当前状态缺少可接受的最新复验；
- `never_verified`：没有严格结构化验证证据。

## 分工

- Skill 定义来源优先级、schema（数据结构）、状态合并和硬门语义。
- 确定性脚本生成 registry、事件、测量摘要和动作许可。
- 项目 extractor 构建设计上下文；项目 adapter 了解 TOML、filelist、结果字段和日志语法，并把上下文作为观察事实交给登记簿。
- Registry 独占当前模块事实和当前集成主线投影；若项目另有通用 Transaction Ledger，它只能作为结构化事件来源，不能成为同一主线的第二个可独立修改副本。
- controller 独占写入时机、配置修改、命令执行和动作阻断，但不保存第二份 pending 模块事实。
- Pro 或其他模型只能消费热视图并提出选择，不能覆盖硬门。

## 可迁移性与接入

迁移到新项目时只需实现一个 adapter，将项目输入映射到统一观察包，并配置 Skill 路径。模块名、服务器、Docker、回归长度、分区名称和工具命令都不写进 Skill。新项目也可以增加层次关系、功耗或物理实现测量，只要保留证据来源和可比性语义。

第一版不限制只保留最近 100 轮。模型读取量由热视图控制，完整事件和测量继续追加，以免过早引入归档、恢复和审计断点。以后历史规模真正成为问题时，再增加按数量、时间和里程碑组合的冷归档策略。

## 不证明什么

登记簿只证明它引用的证据和当前配置状态。它不会把分区 ABC proxy（代理测量）升级成完整芯片 Fmax（最高工作频率），不会把带黑盒 STA（静态时序分析）升级成完整顶层闭合，也不会因为 Yosys exit 0 或文件存在就宣称模块正确。
