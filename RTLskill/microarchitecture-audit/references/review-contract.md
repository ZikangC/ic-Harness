The host supplies the same frozen original closure (spec.md, reference.py and declared support/<input-relative-path> helpers/configuration), one unified architecture.md containing the RTL contract and comparison, structured design, budget report, a packet SHA256 and optional prior audit. ## Restricted independent recomputation

If computation is needed, return only this marker and one JSON object:

```
<<<AUDIT_TOOL_REQUEST>>>
{"tool":"recompute","facts":[...],"assumptions":[...],"calculations":[...],"numeric_probes":[]}
```

The host supplies the original-input per-line quantity view. The binder can also resolve explicit quantity selections in frozen proposal sources; these remain proposal evidence. Build audit facts independently using three forms:

- Source: `{id,source:{file,line,number},unit:optional_declared_unit}`. line and number are one based; number selects the displayed quantity on that line. The tool fixes its literal value and supported attached unit. Do not submit value, formula or citations in a source fact. If no unit is attached, declare a nonempty unit and audit that interpretation; the tool does not default to count. Select original spec/reference quantities for required work and proposal quantities for declared resources. A selected proposal number cannot establish an input requirement, and designer fact IDs or receipts cannot replace original-source selection.
- Conversion: `{id,convert:{fact:existing_fact_id,to_unit:target_unit},citations:optional_source_references}`. The calculator converts supported compatible units, including prefix and bit/byte scales; omitted citations inherit the referenced fact's ancestry. The row has no value, formula or unit field. Convert operands before combining differently scaled quantities. Use this form instead of an arithmetic multiplier for unit conversion.
- Derivation: `{id,formula:expression,unit,citations:[source references]}`. State an engineering relationship over independently bound or converted facts. A shape product, inclusive cardinality or operation repetition is a derivation, not another source literal. The script computes the expression but does not infer the relationship or completeness.

Assumptions remain `{id,value:number OR formula:expression,unit,basis}`; mark uncertainty and never overwrite facts. Calculations remain `{id,formula:expression OR value:number,unit,basis,expected:optional expression}`, exactly one of formula/value. Names reference facts, assumptions or earlier calculations; arithmetic + - * / // % ** and ceil/floor/min/max/abs only. No code, paths, imports or native tools. Optional expected records a comparison; a mismatch can support a finding rather than a tool failure. Source binding receipts record raw declarations, selected token/unit and materialized values against the frozen source version. Successful binding does not prove semantic relevance.

Optional `numeric_probes` uses the shared fixed point-boundary kernel through the following complete request contract; no additional design reference needs to be discovered or read. Select inputs and proposal formats independently. Scalar operations `identity`, `exp`, `sigmoid`, `reciprocal`, `sqrt`, `rsqrt` use `{id,operation,input,format:{bits,fractional_bits,signed},rounding,overflow,assertions,basis,references?:[...]}`. Scalar result metrics are `raw`, `integer`, `quantized`, `lsb`, `minimum`, `maximum`, `abs_error`, `overflow_count`, `zero_count`. Bits are integer 1..128, fractional_bits 0..128 and signed is boolean. Rounding is exactly `nearest_even`, `nearest_ties_positive`, `half_away`, `toward_zero`, `floor` or `ceil`; the tie rules differ, especially for negative half steps. Overflow is `saturate` or `reject`.

`operation:"encode_row"` uses the same fields plus `scale`, a finite positive uniform row scale. Its `input` is an array of 1..4096 numeric values or safe expressions; its format requires `signed:true` and `fractional_bits:0`. Scale is applied before rounding and overflow. Each returned probe has numeric metrics in `results` and row details in `encoding`: `inputs`, `scaled_values`, actual integer `codes`, `decoded_values` (code/scale), and `argmax_rule`. Row assertion metrics are exactly `count`, `scale`, `cosine`, `cosine_defined`, `max_absolute_error`, `reference_argmax`, `encoded_argmax`, `argmax_match`, `encoded_max_ties`, `introduced_tie_pairs`, `saturation_count`, `overflow_count`, `zero_count`. Both argmax metrics use the smallest index among tied maxima; encoded_argmax uses the actual integer codes. Introduced tie pairs count unequal inputs made equal by encoding. Cosine compares original values with actual codes; a zero-norm row gives `cosine:null` and `cosine_defined:0`, and a cosine assertion then fails. In a recompute result the probe objects are at `numeric_probes.probes[]`; arrays in encoding are inspection evidence, not expression identifiers.

Each assertion is exactly `{metric,relation,expected}`, where metric names one result above and relation is `==`, `!=`, `<`, `<=`, `>` or `>=`. Expected, input, scale and format expressions may use independently bound facts, assumptions, earlier calculations and earlier successful probes' scalar `<id>__<metric>` outputs, with the safe arithmetic functions listed above. They cannot reference the current probe by its output ID, a later probe, arrays or null. Select the current probe's actual value with metric. Empty probe arrays are `not_checked`; `assertions:[]` is `computed_only` with `pass:null`, never numerical pass. False assertions remain executed comparisons with `matches_expected:false`; declaration/domain errors make recompute invalid. Finite numeric outputs have actual `<id>__<metric>` calculation IDs; no ID is invented for null or an array. Choose applicable assertions independently and distinguish concrete point evidence from reachable-range, hardware approximation or end-to-end accuracy evidence.


A capacity comparison for virtual frozen spec lines `1: history=3` and `2: channels=5`, requiring all history/channel elements simultaneously, and proposal lines `1: slot=8 bits`, `2: allocation_A=120 bits`, `3: allocation_B=80 bits`, declaring dense slots with no spill/recompute:

```json
{"tool":"recompute","facts":[{"id":"history","source":{"file":"spec.md","line":1,"number":1},"unit":"count"},{"id":"channels","source":{"file":"spec.md","line":2,"number":1},"unit":"count"},{"id":"slot","source":{"file":"architecture.md","line":1,"number":1}},{"id":"allocation_A","source":{"file":"architecture.md","line":2,"number":1}},{"id":"allocation_B","source":{"file":"architecture.md","line":3,"number":1}}],"assumptions":[],"calculations":[{"id":"required_bits","formula":"history*channels*slot","unit":"bits","basis":"simultaneous source elements in the proposal's dense slots"},{"id":"deficit_A","formula":"max(required_bits-allocation_A,0)","unit":"bits","basis":"required minus actual allocated capacity","expected":"0"},{"id":"deficit_B","formula":"max(required_bits-allocation_B,0)","unit":"bits","basis":"required minus actual allocated capacity","expected":"0"}]}
```

The host executes the shared frozen calculator through this skill's script and returns real results. Audit calculations are separate analysis artifacts and never update the design. ## Native realization cost recipes

Use these supported primitives inside a transformed count row's physical_realization. Shapes are positive dimension expressions; references bind the actual selected implementation. These recipes calculate its declared native work, not a source-semantic proof or required hardware instances.

- `{id,kind:"gemv",input_elements:K,output_elements:R}` derives `R*K` MAC for an input vector of K elements producing R outputs. `{id,kind:"dot",width:K}` derives K MAC.
- `{id,kind:"matmul",lhs:[dimensions],rhs:[dimensions]}`: rank 1/2 operands with matching contracted dimension; program derives MACs. Batch/repetition belongs to scope, not a free batch multiplier.
- `{id,kind:"elementwise",shape:[dimensions],ops_per_element:positive_integer_expression}`: program multiplies logical elements by explicitly explained scalar effects.
- `{id,kind:"reduction",shape:[dimensions],axis:zero_based_integer}`: program derives `(axis_length-1)` reductions for every other group.

The program sums steps by primitive unit and compares them with the actual cost-group unit/rate; a custom unsupported unit mapping stays unverified. Use one scope recipe for the mapped candidate workload: element `{kind:"element",axis:string,multiplicity:expression}`, task `{kind:"task",axis:string}`, or prefix `{kind:"prefix",axis:string,prefix_axis:distinct_string,first:expression,step:expression,multiplicity:expression}`. Element contributes N*multiplicity; prefix contributes `N*(2*first+(N-1)*step)/2*multiplicity`; task has one occurrence and may use workload_elements in a whole-task shape. Per-occurrence shapes cannot also use workload_elements. Scope labels do not prove actual repetition or semantic equivalence.

source-analysis.json exposes only verified successful source transactions; full raw results and execution sidecars remain preserved. Failed dependencies stay missing. Source transaction IDs are not proposal observations: use actual check_proposal or recompute receipts. Partial source coverage supports local checks, stays explicitly partial and prevents reuse as a fully successful cached baseline; it never changes source ok=False to true. Its effect on the draft verdict depends on whether a critical semantic or budget question remains unresolved. A bad source declaration is an audit preparation error, not a design defect.

If unresolved correspondence prevents judging a critical effect or the main budget, use unverified and insufficient_evidence; a demonstrated structural contradiction warrants revise. These rules constrain review evidence but do not mechanically establish its semantic truth; behavior evaluation must test it.

Workload correspondence compares complete logical tasks. Before counting or binding flows, check source and proposal profile extents. Flow groups use id, nonempty unique flow_ids, workload, unique traffic_ids (possibly empty), basis and optional references. All grouped fields have the same direction and independently executed source profile; source fields and actual traffic records may receive credit only once per profile. The script computes required bytes from complete-task source bits/bytes and available bytes from effective payload, never wire padding. Byte-aligned fields sum exact payload bytes; nonbyte fields use ceil(sum complete-task bits/8) as a necessary packing lower bound, not proof of a realizable ABI. Zero-activity fields can require zero supply. Each group produces flow_binding and candidate_inventory_bound checks with unit=bytes, source/candidate profile, direction, required/available/deficit and actual source/traffic IDs. The second uses every actual selected traffic record for that direction/profile, including paths omitted by the auditor. It is decisive only when inventory coverage is complete and every relevant quantity/direction is supported. A bound subset failure with sufficient complete inventory can be an auditor mapping error; a complete inventory deficit contradicts the declared candidate and source correspondence, not every possible architecture. Both interpretations still require original-source/proposal review.

Service resources may also be `{kind:"macro_reads|macro_writes",reference:"actual macro name"}` using actual macro count/ports. For candidate-selected expansion, a demand can include `representation:{input_bits:expression,stored_bits:expression}` grounded in that candidate path; the tool does not infer expansion from Python dtype. Intervals are half-open, within the computed task window. Union capacity prevents overlap from adding fake service; different resources and compute may overlap. A necessary service bound does not prove producer readiness, latency hiding, ordering or a complete schedule. Missing audit intervals/mappings leave that tool evidence uncovered, not automatically the draft unacceptable. A credible representative supply mechanism and coarse task schedule with bounded overhead can support RTL exploration; missing major supply organization or an unsupported main throughput claim is a design gap. Detailed arbitration and cycle-exact scheduling can remain implementation evidence.

For a generic source `tmp=a[:,None]*S; nextS=tmp+u[:,None]*v[None,:]; y=nextS@x`, materializing each intermediate can require five state-word accesses per element (three reads, two writes). With ready vector operands and no outstanding consumer needing an overwritten old row, a row retained in priced registers can form nextS, consume it for y and commit it once: one old-state read plus one final-state write per element. The row storage, other operand traffic, arithmetic and numerical behavior still need accounting. This is a valid alternative to test, not a required topology or a universal traffic minimum. Charge materialization when the selected schedule actually uses it; do not infer it from Python arrays or use its cost to reject every fused implementation.

ABI geometry checks use the same `check_proposal` request with optional `model.abi_checks`. Each row is `{id,geometry:<independent fixed recipe>,claims:[...],references:[original and proposal spans]}`. Rebuild the chosen geometry from original shapes and the frozen proposal's explicit layout, not from the designer's formula result. IDs are identifiers; numeric inputs are safe expressions. Lengths/alignment/beat sizes are bytes, element/carrier widths are bits, and dimensions/indices are counts; explicitly convert source scales before using them. The shared integer kernel supports these recipes:

- `region`: `{id,kind:"region",fields:[{id,payload_bytes,alignment_bytes}],beat_bytes}`. Relative offsets of ordered fields each align from the previous end. Check the chosen base separately for compatible absolute field alignment; this recipe does not infer it. Results: `payload_bytes`, `extent_bytes`, `contiguous_wire_bytes`, `contiguous_beats`, `field_beats_lower_bound`, `field_wire_bytes_lower_bound`, and `f_<field_id>__offset_bytes/end_bytes/payload_bytes/padding_before_bytes`. Distinct field-covering beats are a lower bound, not a schedule to skip padding.
- `axis_pack`: `{id,kind:"axis_pack",shape:[...],axis,element_bits,carrier_bits,probes:[{id,logical_index:[...]} OR {id,packed_index:[...],lane}]}`. Byte-sized carriers, C-order and low-bit-first slots only; optional `order:"C"`, `slot_order:"lsb_first"`. Results: `slots_per_carrier`, `packed_axis_extent`, `carrier_count`, `packed_bytes`, `padding_bits_per_carrier`. Probe results: `carrier_index`, `carrier_byte_offset`, `element_bit_offset`, `logical_axis_index`, `packed_axis_index`, `lane`, `logical_<axis>` and `packed_<axis>`. Illegal indices/padding slots fail declarations.
- `beat_span`: `{id,kind:"beat_span",payload_bytes,beat_bytes,probes:[{id,byte_offset,size_bytes}]}`. Results: `payload_bytes`, `full_beat_extent_bytes`, `beats`, `tail_padding_bytes`, `last_valid_bytes`. Probe results: `aligned_byte_offset`, `byte_lane`, `first_beat`, `last_beat`, `spanned_beats`. Probes must remain within valid bytes. Full-beat reads require the returned extent; masked writes/allocation need their actual proposal policy. Test legal nondivisible tails.

Recipe metadata may include basis/references; other orders/packing remain unsupported, not silently approximated. Recipe output values are computed by the fixed kernel. A claim is `{id,result,probe?:<probe id>,declared:<expression OR {traffic_id,metric}>,relation:"=="|"<="|">=",references:[proposal spans]}`. `result` selects the recipe result. For a probe, `probe` separately selects its geometry.probes[].id and `result` is the bare metric name; do not concatenate the ID and metric. For a generic beat_span probe named `boundary`, the claim is `{"id":"cross_check","probe":"boundary","result":"spanned_beats","declared":2,"relation":"==","references":[{"file":"architecture.md","start":1,"end":1}]}`; the cited proposal must actually declare that value. The comparison is recomputed expected value `relation` proposal-declared actual value. For example, necessary full-beat allocation uses expected extent <= declared allocation; an explicitly contiguous image uses expected wire == actual declared transfer wire. Do not impose contiguous transfer on a proposal that legally skips padding.

Expressions use independent executed source facts as `source__<fact_id>` and fresh selected proposal values as `proposal__<value_id>`, with no overwrite. Axis probes additionally expose logical indices `i0`, `i1`, ...; packed indices `p0`, `p1`, ...; and `lane`. Beat probes expose `byte_offset` and `size_bytes`. These let the auditor test the proposal's stated formula at a chosen concrete point. For actual traffic, `{traffic_id,metric}` selects `wire_bytes`, `total_bytes` or `transactions` directly from the freshly computed selected traffic ledger; never submit a replacement actual number. The scope of that traffic record still has to match the comparison.

Each claim produces a bound `topic:"abi"`, `kind:"abi_geometry"` check and existing local transaction receipt. A failed comparison needs the existing explicit counterexample disposition. A declaration correction must retain the same recipe ID/kind, metric/probe and actual target; changing a point or unrelated target cannot close it. Invalid or unsupported geometry produces a failed declaration with no comparison or invented values; disclose its unverified scope rather than treating that as a hardware failure. No ABI coverage-complete label is inferred from a few probes. Independently inspect directory completeness, actual variable meanings, region allocation and other layouts. If allocation or a necessary layout choice is absent, report a design gap rather than invent its value or call an inferred overrun proven.

Operand checks challenge a concrete issue against actual window uses. Each issues row lists the actual active lane indices and required operand roles at its cycle; a tool claim of a full issue requires every lane of the referenced cost group's actual units, and MAC issue needs both input roles. A single-lane witness stays partial and cannot be relabeled as complete by prose. Partial tool coverage may still support a representative engineering argument when the remaining mapping and conservative utilization basis are explained; exhaustive full-lane expansion is not a delivery requirement. Existing finite word/port/ready-cycle checks still apply. Broadcast slices may reuse one word. Optional local_uses supplies register or feedback operands as `{kind:"register"|"feedback",buffer,cycle,lane,operand,width,bit_offset,ready_cycle,basis,references:[proposal spans]}`; feedback uses additionally require feedback_basis explaining the producer/iteration. The buffer must be an actual candidate register buffer, with proposal evidence for the value and timing. Physical and local supply cannot duplicate the same cycle/lane/operand position. Slices outside that buffer's capacity and uses before ready_cycle produce failed comparisons; window/lane bounds and field errors fail the declaration. Capture/producer semantics and simultaneous holding lifetimes still require independent review. Unsupported paths/partial coverage stay unverified, not invented port failures.

The result distinguishes successful declarations (`ok`), coverage_complete and each check status pass/fail/unverified. Independent count/flow/service/operand transactions have executed or declaration_failed status. Successful subreceipts preserve checks, observations and qualified values, binding the complete original/frozen packet, source analysis, proposal, budget, declaration and checker/calculator closures; the top values are exactly their union. The host verifies these identities before listing usable references. Missing source/profile/count/fixed-flow/service-declaration/critical-operand coverage remains a diagnostic of this tool request, not a universal release gate for an architecture draft. Missing external service capability remains unverified with explicit conditions. A calculated deficit is an executed comparison, not a malformed request. Every binding-verified failed check from every request must be adjudicated for every final verdict; neither a later request nor insufficient_evidence can silently erase it. Every claimed passing relationship must hold; executed failures remain preserved and explicitly adjudicated even when they reflect an auditor declaration error. Correct arithmetic and version bindings do not prove semantic completeness or physical closure.

## Final report

If an executed `check_proposal` receipt lists `missing_service_checks`, an `accept` report must use both `checks[topic="resource_service"].status="conditional"` and an `unverified` row with `kind="implementation_evidence", topic="resource_service"`. In this row the topic is the machine classification; put the specific service description and remaining proof in `obligation` and `reason`. These are report fields, not a request for new architecture evidence.

Return `<<<AUDIT_REPORT>>>` followed by one JSON object (not Markdown, narration or native tool markup). A bare JSON object is also accepted. Never put a second JSON object after it:

```
{
 "scope":"what was actually audited; missing evidence and limits",
 "verdict":"accept|revise|insufficient_evidence",
 "requirements":[{"id":"extracted constraint id or additional independent id", "requirement":"source requirement", "baseline_ids":["independent baseline id"], "status":"covered|missing|contradicted|deferred", "explanation":"why", "references":[...]}],
 "checks":[{"topic":"requirements|cycle_accounting|resource_service|abi|numerics|area_basis", "status":"pass|conditional|fail", "evidence":"specific reasoning", "references":[...]}],

 "counterexample_reviews":[{"request_id":"actual returned id","receipt_id":"actual child id","check_id":"actual failed check id","disposition":"design_defect|audit_declaration_error|source_interpretation_error|unresolved","reason":"specific interpretation and closing evidence","references":[original_source_ref,proposal_ref],"finding_id":"for design_defect","correction_check":{"request_id":"actual returned id","receipt_id":"actual child id","check_id":"related actual passing check id"},"baseline_obligation_id":"for source_interpretation_error","unverified_topic":"for unresolved"}],
```

For accept, every extracted constraint and independent baseline id must appear in requirements; that alone does not prove semantic completeness. Negative/insufficient reports may list only the portions actually reviewed: the program records missing baseline/constraint IDs and release_mapping_complete=false rather than forcing a complete mapping to report a local necessary defect. Never claim such a partial report establishes full acceptance coverage. Independently add source requirements omitted by extraction. Covered/deferred rows and each of six checks require both original-input and proposal references. A covered row establishes defensible source-to-proposal correspondence at this design stage, not completed RTL simulation; explain the required effect, implementation decision and remaining proof. It need not have a separate receipt for every source function or complete count/flow/service/operand execution. Explain a credible resource and cost basis and disclose what remains unproved; optional tool coverage cannot replace that judgment. Missing/contradicted rows require input evidence; use a relevant proposal excerpt for omissions if possible. Deferred calculable hard design budgets are invalid. Findings and unverified obligations need references. All prior open blocking findings require revision_checks entries; an unverified rebuttal is not resolution. Accept requires no failed report checks or missing/contradicted requirements, no open blocking finding or prior blocking finding, and a source-backed engineering basis for resources, critical choices and budgets. Quantitative evidence must include at least one actual same-packet binding-verified check_proposal child transaction and independent numerical observations; no all-count/all-profile/all-operand coverage_complete flag is required. These necessary checks do not establish that evidence actually supports a conclusion.

Conditions require condition_kind=external or implementation_evidence. Every unverified item requires one of three kinds: audit_evidence for an unresolved critical review question (source semantics, state safety, main supply/capacity or hard budget); design_decision for an absent consequential architecture choice; implementation_evidence for later detailed pipeline/arbitration/tail design, execution/regression or physical validation supported by a credible architecture-level choice. Accept with audit_evidence or design_decision is invalid. For an audit-evidence gap, name the concrete unanswered question and next audit action; do not turn a missing receipt into a proposal defect or RTL obligation. An undefined critical numerical path, consequential ABI ambiguity, state-lifetime error or missing major supply organization is a blocking design issue requiring revise. Exact pipeline stages, arbitration and tail-control details need not be fixed if their functional policy and resource/cost implications have a credible bounded basis. Complete major budget components and explicit supply/resource assumptions, including justified conservative utilization or estimate ranges, can support a conditional engineering estimate; whole-chip RTL cycle consistency, stress simulation, numerical execution and physical timing remain downstream evidence. Optional suggestions do not block delivery or require continued optimization. The labels alone do not prove correct classification, and no kind alone creates an evidenced design defect.

counterexample_reviews contains exactly one row for each actual binding-verified failed check, identified by request/receipt/check IDs. This includes valid ordinary `recompute` comparisons with `matches_expected:false`, including numeric assertions. The program exposes those comparisons through the existing check-reference list with `receipt_id:"recompute"` and `check_id` equal to the actual comparison ID (a calculation ID, or `<probe_id>__assertion_<zero_based_index>`). This is a program view of the executed comparison, not a model-authored receipt. `ok:true` means the calculation executed; it does not close a failed comparison. A comparison may reflect a wrong auditor assumption rather than a design defect, so do not automatically turn a mismatch into infeasibility. Every such failure must nevertheless receive a disposition; an `implementation_evidence` label or a future possible architecture cannot close it. This verified identity itself cites the actual immutable check and program-owned quantities; do not copy another calculation ID merely to reference the same failure again. Additional evidence references can use numeric {request_id,calculation_id,actual} or {request_id,receipt_id,check_id}; either must identify actual bound execution. Numeric observations still need their real calculation IDs and matching numeric actual. Never invent a number for a diagnostic list. Only supply fields relevant to its disposition. design_defect links an open blocking category=design finding and requires revise even if other audit evidence is missing. audit_declaration_error needs original-input/proposal evidence and correction_check selecting an actual passing check with the same check identity/topic/kind against the same frozen packet. Flow corrections preserve source flow IDs/profile/direction/required bytes; correcting a mistaken source-to-candidate profile mapping may change the candidate profile, but the reporter must justify the semantic correspondence. Count corrections preserve actual source paths/profile/unit, and native-cost corrections preserve the actual cost-group identity; a direct source-count correction also preserves source demand. A smaller unrelated expected demand or passing arithmetic cannot rebut the failure. source_interpretation_error links an explicit baseline_corrections entry with original-only references and actual analysis_targets: affected source declarations/profile, or their actual fact dependencies. An unrelated baseline obligation/area correction cannot hide a payload deficit. This does not fabricate a corrected result, rewrite the baseline, or allow current accept. unresolved requires insufficient_evidence and a corresponding audit_evidence or design_decision unverified entry explaining the unresolved correspondence. A complete inventory deficit cannot be filed merely as unresolved/downstream evidence: classify a real defect or supply a concrete source/profile correction. For a recompute `audit_declaration_error`, `correction_check` uses another actual `receipt_id:"recompute"` comparison against the same frozen packet. Preserve the actual comparison ID, target/unit (or numeric operation, input and asserted metric), relation and required expected value. Execute the changed source selector, assumption, expression or format declaration; changing only the expected value or pointing at an unrelated pass is invalid. The program requires a related source dependency, or a new proposal-bound dependency when the old probe used only literals. Cite original/proposal evidence and explain why the revised interpretation matches the same obligation; lineage and arithmetic do not prove that explanation true. A narrow guard rebuttal may instead select a different actual passing comparison: the new request must reproduce and consume the original failed measurement with its unchanged input/dependency lineage, then apply a guard independently selected from the same frozen proposal. For example, a rounded intermediate may legally be zero when the already specified denominator guard handles it; positivity of that intermediate was an auditor premise, not necessarily a chip requirement. The program checks reproduced measurement lineage, dependency on new proposal evidence and real execution. It rejects changing the point, merely changing expected, a literal invented guard or an unrelated passing probe. The auditor still determines whether that guard is the specified applicable mechanism and preserves the original requirement; this is not proof of every guard or permission to invent one. A recompute `source_interpretation_error` needs an explicit original-backed baseline correction targeting a source declaration related to its selected inputs, and cannot enable current accept without a newly executed corrected source version. `unresolved` requires `insufficient_evidence` plus a named critical audit/design question. The host enforces tracking and related executed comparisons, not the truth of prose interpretation. A failed auditor declaration is not automatically a chip defect.

Report validation checks references, calculations and internal contradictions. It does not prove requirement coverage, independence of reconstruction, schedule correctness, numerical behavior, cost-source truth or physical closure. Program release authority remains with the caller.

## Repair scope

Engineering review order and evidence classification are defined in SKILL.md. This contract specifies tool/report transport and validation; it does not add architecture requirements. Executed rule expansion, numeric assertions and direct schedule-cost binding support the particular declared relationships; none proves source semantics or closes an unrelated path. Empty or calculation-only numerical evidence cannot be cited as a numerical pass. For a blocking finding, `required_change` gives a testable closure criterion without prescribing a preferred organization. An unsupported audit declaration or missing receipt alone is not a hardware failure.

The host separates executed tool history, current report repair feedback and previous_audit. A rejected report stays a current-report draft, never the previous architecture audit. revision_checks maps only the exact supplied prior open blocking IDs; use [] if none. During report repair preserve the unchanged packet and valid receipts. Program validation errors are not chip requirements and do not themselves become architecture findings.

Use the host's exact baseline-id and binding-verified executed-calculation-reference lists. A failed recompute contributes no valid observation. check_proposal instead retains separate successful transactions when an independent declaration fails; only the host-listed qualified calculation IDs are usable. Local success proves only its declared relationship; the report separately explains whether remaining gaps matter to the draft verdict. Repair a small failed recompute before optional lookups. If tools remain and a concrete unresolved hypothesis could establish a necessary change, test it before ending on evidence gaps. No tool failure or missing receipt alone proves a design defect; no absence of failed checks proves there is none. Report revise for an independently evidenced structural defect, otherwise insufficient_evidence only when a critical review question prevents a defensible draft judgment. Incomplete optional tool coverage alone is not such a question. Never fabricate an observation.

Transport feedback distinguishes JSON syntax, protocol fields, failed evidence requests, report validation and valid semantic judgments. A content-preserving syntax repair may be executed by the host for a complete single JSON frame; it is separately charged and never supplies missing content or changes findings/values. Report validation feedback is not a new architecture finding. A failed recompute cannot supply an observation: repair it if it is necessary to the judgment, or disclose the unsupported scope; an executed mismatch still needs interpretation against original inputs and proposal.

An external_requests resource may instead supply capacity_source:{file,line,number} and optional unit, independently bound from original inputs by the shared binder. Do not supply capacity_fact at the same time. The real binding receipt is preserved; this path works when the selected source quantity expresses a rate, or has no attached unit and the original context justifies that semantic unit. An attached unit remains authoritative: a counting word bound as count cannot be overridden or converted into requests/cycle. A recognized adjacent compound rate can use capacity_source directly without a baseline fact. Relationships that the lexical unit does not encode still need the explicit source-backed derivation described in source-baseline.md, executed as a baseline fact and selected through capacity_fact; multi-cycle statements are not inferred into instantaneous per-cycle capacity. The proposal entry cannot silently add a missing fact to its frozen baseline. Distinguish that evidence gap from a physical condition absent from the original inputs.
