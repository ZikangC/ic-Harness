# Harness 通用设计流程

本文说明可复用的流程边界，不定义任何具体芯片、模型或测试数据。当前已实现环境配置、环境检查与微架构阶段；RTL实现、Readiness和PPA仍为后续边界。微架构入口和证据范围见 `../ARCHITECTURE.md`。

## 输入与可移植边界

默认读取项目内 `input/spec.md` 和 `input/reference.py`，参考只作文本/语法分析，不执行。多文件参考可用可选的 `input/sources.json` 显式声明：

```json
{
  "schema_version": 1,
  "spec": "spec.md",
  "reference": "model/entry.py",
  "support": ["model/helpers.py", "config.json"]
}
```

所有路径都相对 `input/`；`support` 列出需要冻结的 helper/config 文本，不自动发现或读取未声明的本地依赖。每份原始文件保留字节内容及指纹。模型收到的主名仍为 `spec.md`、`reference.py`，支持文件使用 `support/<实际相对路径>`。非标准路径的参考入口也自动保留在 `support/` 原路径下，便于理解包目录和 import 关系；它与 `reference.py` 是同一文件的两个名字，不重复计工作量。

需求提取、设计、独立源基线及方案审阅都收到同一完整原始输入闭包，允许引用其中相关 helper/config；审阅不继承设计上下文。声明闭包与引用有效不证明源解释正确，也不要求把每个 helper 都转成独立义务。仅 spec 的运行方式仍属于后续扩展目标。

harness不得要求参考文件拥有某组固定类名或函数名，也不得内置模型尺寸、张量名称、seed、镜像ABI、芯片接口或硬件预算。阶段应从当前输入提取这些条件，区分明确要求、实现选择和待澄清项。规格与参考有冲突时报告冲突，不能静默覆盖。

harness可以包含通用工具适配与环境配置。具体项目的数据转换、镜像构造、测试平台、数值模型和实现约束若需生成，应放在 `output/<run_id>/`，并注明所依据的输入身份。通用机制不能从旧项目目录读取文件，也不能依赖上一次运行的输出才能处理新的input。

复制harness并更换input后，在执行环境兼容的前提下，应能够启动新项目的需求提取。迁移至其他机器时，工具路径、连接方式和认证仍需适配；凭据不保存在设计输入或生成产物中。

## 阶段职责

微架构设计提取功能、算子依赖、状态生命周期、访问需求与硬件约束，提出少量候选并评估计算、周期、带宽、容量和端口需求，形成适合 RTL 探索的选定草稿及实现契约。主要预算可用典型路径、粗调度、有依据的保守利用率和估算范围支持；完整逐拍排程、局部仲裁、尾部控制和完整位精确回归可由实现阶段细化并回填。已知功能语义或状态顺序错误、容量不足、主要计算或带宽预算明显不成立仍须本阶段解决。共享、分块、多周期和流水方式由具体需求决定，不能将参考程序调用直接映射成独立硬件实例。

RTL实现落实选定方案，同时生成适用于当前项目的功能、协议和数值验证。Readiness检查RTL是否落实方案并具备后续实现条件。PPA优化改善已有功能验证的实现；影响接口、延迟或架构契约的修改须回到相应评审。

必要的局部综合用于校准方案估算，不能代替完整实现的资源和时序验证。缺少关键条件时可交付带条件的候选分析，但不能将其称为已满足全部预算的实现。

## 产物与证据

运行产物保存在项目的 `output/<run_id>/`，生成源码使用显式filelist。证据绑定当前输入、选定方案、源码、验证组件、工具版本、实现库及存储模型的内容身份。

基础设施失败、测量未完成、功能或协议失败、预算不满足分别报告。未运行的检查标为未验证，不组合不同候选或不同测量范围的证据；历史结果不能证明新的输入或实现正确。

执行时间、调用额度和重试限制由harness配置管理。芯片面积、存储、时钟与吞吐条件来自input，不能由执行预算替代或自动修改。

微架构阶段已接入这些边界，但不包含RTL生成验证链。可移植性需要通过更换input的实际运行验证。
