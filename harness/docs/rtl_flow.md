# RTL implementation and independent audit through local OMP

The ordinary RTL stage invokes two portable skills: rtl-implementation generates a substantive first version and development checks; rtl-audit independently checks one frozen candidate and returns its source-bound verdict and findings. The caller selects the repair executor and starts a fresh audit for each returned candidate. Ordinary RTL generation explicitly selects the implementation skill; the optional readiness workflow can select its own editor. Debugging and acceptance run without an external conversational operator supplying individual bug diagnoses.

Run `python3 harness/run.py rtl --run-id NAME` locally. OMP uses the configured implementation/review roles and existing authentication. The configured SSH host/container executes all numeric, simulation and EDA work. RTL, data, snapshots, full logs, frozen candidates and evidence remain under server output/NAME/. Temporary local model/tool context is removed on exit. There is no total model-call or elapsed-time cap; individual jobs have explicit timeouts. The skills must report repeated lack of progress and real external blockers instead of looping indefinitely.

Use --validate-inputs for a read-only input/architecture/harness identity check, --task task.txt for a frozen implementation task and --resume NAME for interrupted work with identical inputs, configuration and harness. --audit-only --resume NAME resumes the ordinary RTL review/repair loop without repeating generation; it retains the explicit implementation repair policy. For a review without any automatic repair, call the harness adapter's `review_once` API or invoke the audit skill directly with its inputs and report scope. A changed skill or configuration requires a new run; historical snapshots are never replaced. A resumed audit with a completed valid pass reuses its decision. A previously blocked/evidence-insufficient audit gets a new review scope to check recovered external conditions. An interrupted publication cannot inherit an unrelated old session receipt.

The controller freezes input and skills, dispatches model/tool calls, records lifecycle and manages recovery. It does not choose hardware methods or infer acceptance from logs. The harness-owned adapter in `harness/adapters/rtl_audit.py` follows the audit's explicit decision. With an explicit repair handler, revise can invoke that executor and then a fresh audit; without one, revise returns without source changes. Pass, insufficient_evidence and blocked finish the review without source repair. `review_once` performs only one candidate's audit. The audit skill package contains no repair-loop scheduler and does not require the implementation skill. rtl_stage_release records the independently authored, mechanically bound pass decision. It is not a proof or a full physical-closure claim; the legacy implementation_verified remains false. CLI exit zero and normal model termination alone do not establish correctness.

The initial implementation context carries the complete frozen primary specification and reference texts with their input fingerprints. They are passed through without an architectural interpretation or acceptance summary; support files and the architecture remain available through remote aliases. This supplies the source requirements even if the model would otherwise read only the architecture or execute the reference as an oracle.

Fresh independent audit and repair contexts also identify the frozen candidate's architecture packet explicitly. The controller requests its verified primary architecture material when starting each role: the complete narrative, source/provenance and decision texts when present, plus the packet's file index and fingerprints. These are original engineering inputs, not a controller interpretation of the design or additional tool permissions. The frozen candidate baseline is distinguished from a subsequently changed run-current packet. Design declarations, budget results and review evidence remain available through their indexed paths; missing provenance is explicit and never becomes approval. A pointer status, copied planning note or absence of a new-run revision folder does not establish an architecture mismatch.

Remote text reads return exact UTF-8 `content`, the legacy numbered `text` display, source SHA-256 and identity, and an exclusive `returned_range.byte_start` / `byte_end` with one-based Unicode line/column positions. The response is bounded to 24,000 UTF-8 bytes of JSON, so even one long line can span pages. `truncated` explicitly says the requested line window exceeded that bound; `eof` says whether this page reached the file end. While `next_cursor` is present, continue with the same `path` and that `cursor`, without `start`; use `content` to reconstruct bytes including original line endings. The cursor continues from the exact next byte, including within a long line, and remains available when the line window ends before EOF. It is bound to the run, scope, alias, resolved source and content hash; changed files or a different context require a fresh read. A line number, a file list or a structural JSON projection does not prove complete readback. Existing small numbered reads remain compatible with control-receipt readers.

Control RPCs can synchronously hash and copy complete build trees, so the adapter imposes no overall wall-clock deadline on those calls. SSH connection and keepalive checks remain enabled, and submitted execution jobs retain their explicit timeouts. A worker stuck behind a healthy SSH connection may require operator interruption. Transport failures raise ConnectionError, distinct from a server-side missing receipt; the coordinator must not treat an uncertain read as permission to repeat a completed model session. Transport failure or interruption does not establish rollback: reconcile the actual server state before any explicit continuation. The adapter never retries a request automatically.

Audit tests live in audit/review-N/; implementation edits stay in work/. Each candidate freezes the complete work tree and its current architecture, including Makefiles, parameters and data files rather than only RTL extensions. Candidates and decided audit evidence remain unchanged through later repair jobs. Historical scripts, binaries and datasets may be read, but all new build products, reports and simulator outputs must target the current writable scope or the job's private temporary directory. Inspect reused scripts and tool output arguments before execution; a historical working directory or absolute output path does not become writable merely because a script is launched from a new scope.

New runs freeze the configured Docker job-isolation identity in their manifest. The trusted host launcher executes each queued command in a separate container using the control container's exact image and user. Inherited data mounts and the image are read-only; only the declared job scope and private disk-backed /tmp and /var/tmp are writable. The launcher rejects unsupported mounts, external hardlinks in the writable scope and configuration changes before execution. It retains network access through the existing control container and passes no Docker socket to the job. There is no fallback to the legacy executor when isolation setup fails. Host Docker access and matching host/container workspace mappings are required; historical runs retain their frozen executor and cannot be upgraded in place.

Job receipts retain the submitted closure, actual start/end source inventories, exact container identity and cleanup outcome. The existing protected-tree guards still check before/after execution. Timeout and cancellation terminate only the job's verified container; a terminal result is accepted only after container cleanup. A cleanup failure remains pending and stops the coordinator for reconciliation. These controls protect engineering evidence against misplaced tool writes; they are not a claim of comprehensive hostile multi-tenant isolation. All copied data stays on the server; complete-tree copying/hashing costs should be measured on large projects before optimizing storage.

Before freezing a candidate or ending a repair, the coordinator waits for existing jobs to produce their actual terminal results. The pending query covers all jobs, including older jobs outside the recent-history window. It neither resubmits work nor interprets exit zero as acceptance. Interrupting this wait preserves detached jobs and completed model receipts; an identical-version resume continues waiting before the guarded transition. A completed audit session that left jobs pending without a decision gets a fresh audit context after those results arrive; a session with no decision and no pending evidence still ends as incomplete. A lost supervisor with no result is not reconstructed or marked successful by this mechanism.

The audit reads original sources and checks functional, numeric and interface acceptance, including specified discrete-selection/accuracy metrics and workloads. Architecture estimates do not add gates. Missing physical conditions and unexecuted requirements are explicitly reported. The audit maintains independent tests and expected values; the repair model cannot silently rewrite them. An invalid audit test can be corrected only with source-backed justification and preserved prior evidence. The audit must reject missing computation, preset outputs and testbench/software substitutes, and score complete output and completion behavior through the actual top.

Hard gates and ideal optimization targets retain the status established by the source requirements and explicit delivery instruction. An unclear target is not automatically a hard gate. A demonstrated material avoidable efficiency defect requires real repair and matched before/after verification. A reasonable engineering tradeoff requires independent evidence on alternatives, feasibility, resource/clock budgets and residual risk. An ideal throughput gap alone does not force an overall failure; an accepted baseline must still disclose an unmet or unproven target and cannot claim target met. Functional, numerical, protocol and explicit hard resource requirements remain intact.

Repairs use reproducible failures, semantic checkpoints and server-side snapshots to localize the first unexplained deviation, then rerun affected checks and final acceptance. Lint/elaboration and focused simulation support iteration; synthesis follows structural risk and candidate milestones. Valid source-bound synthesis evidence may be reused after independent scope/dependency/result checks. Changes invalidate affected evidence. Review reports carry the exact candidate identity, actual current-review job IDs and a source-backed verdict; referenced old jobs are supporting evidence, not current execution.

Major resource, ABI, internal-precision or budget changes use the existing rtl_revise_architecture interface. Optional design and architecture-audit skills run in fresh local OMP contexts, preserving requirements and historical files. Their absence does not block candidate generation and ordinary repair; a missing review is not approval. A failed calculation or review cannot be reclassified as an absent capability. The RTL audit inspects the current architecture decision before release.

During skill development, use isolated behavioral fixtures to test real repair, refusal and recovery without supplying answer keys or repair hints to the model. Small fixtures establish limited mechanism evidence; they do not establish quality on the original model. General skill/controller files and original inputs are read-only during project runs. Development improvements produce new frozen skill versions, not project-specific answers embedded in generic instructions.
