# Repair an independently reviewed RTL candidate

Use the provided audit report, frozen candidate identity and current implementation work directory. Read the relevant source requirements, reference and architecture as well as the failed job's actual diagnostics. Preserve earlier candidates and evidence. Runtime repair changes project artifacts in the writable implementation work directory; it does not modify frozen inputs, general skills or audit-owned artifacts. This mode runs only when the caller explicitly routes this candidate to RTL implementation; it does not infer ownership from report prose or schedule a later audit. Report a concrete evidence or environment block without treating every `blocked` or `insufficient_evidence` outcome as an RTL defect.

## Diagnose before changing behavior

Reproduce the reported failure against the current implementation or explain the exact version/environment difference. A report need not name a root cause. Missing computation, unconnected required modules and dummy output paths are implementation failures to repair, not conditions to waive. A numerical or protocol failure is an engineering problem to investigate; do not wait for an external operator to identify each bug.

Check a review's architecture and measurement claims against the actual selected packet, source procedure and existing job results before choosing a change. An inherited plan or prior-version value can be stale. Preserve the source-backed discrepancy when a finding is incorrect; do not change the RTL to satisfy it or rewrite audit-owned evidence. This does not waive independently demonstrated failures in the same report.

For missing computation or top integration, follow a small legal transaction from its supported external initialization/input path to the required state update and output. Implement and exercise the first unfinished resource/state boundary, then extend that working chain through the remaining required stages. Reuse applicable leaf evidence and focused numerical probes to support this work. The first-version minimum case in the main skill remains the integration target; completing more isolated tests does not close a missing executor. Keep the next boundary and runnable reproducer in the implementation checkpoint so a long repair can resume without restarting its exploration.

For a failure that is not locally obvious, use a stable input/configuration and progressively compare semantic boundaries. Keep operand layouts, scales, rounding, state versions and transaction identities explicit. An allowed numerical difference is not itself a defect; identify the first deviation that the source's numerical rules cannot explain. Capture only useful windows and summaries for model interaction. Full tensors, waveforms, simulator products and long logs remain on the server.

Narrow a failing full run to the affected computation or transaction when practical, retaining the relevant state and producer/consumer relationship. A local reproducer accelerates diagnosis but does not replace the final acceptance run. Treat timeouts, missing outputs, incomplete dumps and missing DONE as failures rather than scoring the available subset.

## Structural preflight and diagnostic disposition

Apply this check to generation and repair, before handing off the delivered implementation or launching long whole-design mapping. Keep `RTL_STRUCTURE.json` at the implementation source root so the declaration is frozen with the candidate. Its exact top-level fields are `version: 1`, a nonempty `configurations` array, and `blackboxes` (empty when none are used). Each configuration has a unique nonempty `id` of at most 128 characters, the actual `top` and ordered relative `sources`; `include_dirs`, `defines` and `parameters` default to an empty list/map/map. Include all delivered compilation configurations, with no duplicate semantic configurations. This declaration must match the requirements and actual build; merely declaring a smaller top does not make it the delivery top.

For each authorized external black box, add `{module, kind, reason, source_refs}` to `blackboxes`. `kind` defaults to `blackbox` and may be `whitebox`; `reason` is nonempty, and `source_refs` contain exact frozen requirement, candidate RTL interface and selected architecture paths with SHA-256 values. Use `@input/`, `@candidate/` and `@architecture/` references; this evidence contract binds the architecture alias to the eventual review's frozen copy, so no future review directory needs to be guessed. A box's candidate reference must identify its actual RTL module/interface source, not a self-reference to this declaration. The independent audit checks authorization and the real interface. The runtime compares the declared names/kinds with the union of actual tool-produced reachable module inventories across the checks. A delivered top cannot itself be a black/white box. This declaration permits legitimate external interfaces without approving substituted required computation or claiming missing physical models have been verified.

Use the native check's first trusted fast-lint stage against the complete declared top, ordered sources, include paths, defines and parameters, retaining its complete command, effective tool conditions and original diagnostics. For an early repair decision, explicitly request `execution_plan: "diagnostic_first"` at the action's top level, outside `configuration`. When full-configuration lint completes with target diagnostics, the native job returns a complete negative JSON result and raw transcripts before Yosys; wait for its terminal cleanup before editing. Bitwise coverage remains unclosed. Inspect findings, repair actual defects and submit a new check for the new source. Do not run a complete frontend solely to delay an already justified negative handoff. A separate development-only lint job is optional supporting evidence and must use the same recorded synthesis profile; do not require a duplicate lint invocation or substitute an unrelated default simulation macro view. Use explicit driver/assignment diagnostics rather than relying on a default lint return code. Inspect the implicated bit/path and fix actual RTL defects in the normal implementation work; a lint warning can also describe legal unused bits, sequential holds or an authorized interface, so classify it from evidence instead of treating every warning as fatal. In particular, Verilator lint is not a complete bitwise assignment proof: a partly assigned vector can escape its signal-level UNDRIVEN diagnostic. Keep that coverage limitation explicit. Fast lint does not replace the full native structural check.

For each declaration entry, omit its label `id` and submit `rtl_remote` with `action: "structure_check"`, `configuration` containing the actual `top`, ordered scope-relative `sources`, `include_dirs`, `defines` and `parameters`, and an explicit `timeout_seconds`. `defines` maps macro names to string values or `null`; `parameters` maps names to Verilog numeric-constant strings. Use the supplied schema for the remaining fields. Include the complete synthesizable compilation closure for that top/configuration, including included/generated RTL and declared external dependencies; do not select only a changed leaf or omit a source to silence a finding. Retain the returned native `job_id` and `configuration_sha256`, then query the normal jobs/status interface until its actual terminal result is available.

The native checker uses frozen configuration/result version 2: fast lint first, followed by the complete Yosys frontend under the bound delivery configuration. It retains per-stage tool identities, effective conditions, commands, original byte transcripts and actual outcomes. `fast_lint.profile` records the trusted `yosys_synthesis_v1` macro profile: effective declared/synthesis macros and the fixed Verilator tool-default undefines. Inspect that profile instead of assuming that two frontends share intrinsic macros. Unsupported synthesis-macro overrides or undeclared tool-specific macro branches remain explicit unsupported conditions; this profile is not a universal intrinsic-macro equivalence claim. Omission or explicit `execution_plan: "complete"` preserves the full lint-to-Yosys path, including target warnings, so the independent reviewer can inspect complete evidence for an exact disposition. `diagnostic_first` stops only after successfully completed lint has target diagnostics: `ok` is false, status is `findings`, `coverage.kind` is `diagnostic_only`, bitwise coverage is `unclosed` and Yosys is `not_run`. The action's frozen config/hash binds this intent. Lint clean still proceeds to Yosys; a true lint error, timeout, abnormal exit or missing tool remains unsupported/failed/open rather than a DUT-finding conclusion. Diagnostic-only evidence cannot pass the existing release gate or receive a waiver in place of missing structural coverage. The Yosys stage reads/elaborates the selected top and parameters, inventories actual black/white boxes, then converts processes with `proc -noopt` and runs `check -assert` before mapping. Default process optimization can erase evidence of undriven expressions; do not substitute an optimized or model-authored script. Literal relative include/readmem dependencies inside the source root are supported; dynamic or absolute dependencies are reported unsupported.

Inspect the protected tool log and structured findings as well as the exit/result status. While a native job runs, use its real-time stderr stage logs (`FAST_LINT_BEGIN/END_V2`, `YOSYS_BEGIN/END_V2`) to distinguish progress, a tool failure and actual RTL findings. The terminal stdout is one complete version-2 JSON result; partial/live text is diagnostic evidence, not a completed pass. Check used bits with no driver, partially driven vectors, conflicting drivers and assignment-path diagnostics where the frontend supports them. Distinguish a missing driver or unintended combinational hold from a legal sequential enable/state hold. Top-level input ports are external drivers; declared black boxes need the actual interface and source-backed scope justification. Unused bits, an intended state hold or a blanket warning suppression are not interchangeable explanations for a used undriven bit. Preserve warning categories, exact locations/bit ranges and finding IDs rather than reporting only an error count.

Supporting tools need demonstrated coverage for the actual construct and parameter context. Read their complete raw stdout and stderr, not only a JSON diagnostic view: when using configured Slang-tidy, `--diag-json` can omit later rule diagnostics, so an empty JSON list, quiet output or `--lint-only` invocation cannot establish a clean rule check. Signal-level lint or a tool with known bit-use blind spots needs relevant real-module/parameter-context bitwise or structural evidence; state its boundary and leave missing coverage open. Do not substitute a toy wrapper, omit dependencies or treat a supporting tool as a new mechanical release profile.

For a supplied Slang-tidy v12 tool, its configuration parser uses the following literal format, not JSON or TOML. Write these bytes to a current-scope file (including the final newline), then pass that path with `--config-file`:

```text
Checks:
 -*,
 synthesis-undriven-range=error
```

Invoke a supplied supporting binary through the configured Python executable when it is not a registered executable alias. In that wrapper, use a subprocess argument list with the exact binary and config paths; first retain `--config-file <path> --dump-config`, then run normal analysis with the actual complete compilation arguments. The rule name is a configuration entry, not a command-line flag. Preserve the configuration bytes/hash, binary identity, complete argv, both raw output streams and actual subprocess return code; propagate failures to the job. A dump verifies enabled rules but may omit severity, so it does not replace execution or the original diagnostic bytes. Keep explicit core driver warnings enabled as well: this rule alone can miss a wholly undriven signal. Check the actual published version's help and demonstrated construct coverage rather than trying unrelated configuration formats or interpreting parser failure as an RTL finding.

Live status is a bounded preview. If `counts_complete` is false, totals in `counts` are unknown (`null`); `observed_counts` are only prefix lower bounds. Follow the protected log's read continuation when the preview is truncated or lacks the fast-lint end marker. Zero observed findings cannot support a claim of clean lint, and a later tool timeout does not erase earlier warnings.

Fix actual implementation defects and repeat the affected complete configuration against the final source. Keep prior failure logs and both source/configuration identities. Propagate every tool/command failure to the job result; a wrapper that prints a failure and exits zero does not make the check pass. A missing tool, unsupported construct, cancellation, timeout, changed source or incomplete compilation closure is an unclosed check, not a waiver or success. Preserve the actual live/terminal logs and native receipt before deciding the next action. Do not blindly repeat an unchanged tool failure or merely increase its timeout; identify the concrete tool/configuration/capability condition, and report blocked/open if it cannot be resolved within the supplied interface. An ended session, completed proposal or normal process exit is not evidence that RTL defects were fixed. Report the concrete condition if it prevents a completed handoff. A diagnostic candidate with open checks or findings may still enter independent audit for an evidence-backed repair decision; do not claim its self-check passed, and do not block that review merely because the diagnostic candidate is not clean. Structural preflight supports early diagnosis; it does not replace function, numerics, protocol checks or required final synthesis/physical evidence.

Unknown warning classes remain unclosed and cannot be waived. A recognized lowering warning still yields findings and needs exact independent disposition; it is not an automatic pass. An implementation claim that a diagnostic is intentional is supporting material only. Retain a narrow proposed disposition tied to the exact finding, bit/path and configuration with its specification/interface or actual verification evidence. The independent audit must check and authorize any waiver; broad `-Wno-*` flags, omitted modules or a prior model's confidence cannot supply that authorization.

## Efficiency repairs and tradeoffs

Check whether the cited performance value is a mandatory source/caller requirement, an ideal optimization target or an estimate. Keep all functional, numerical, protocol and explicit hard resource gates intact; uncertainty does not justify silently changing that classification. A target gap alone is not proof of a material avoidable defect. Investigate the actual work, stalls, dependencies and resource/clock limits before attributing avoidability.

When actual evidence establishes a material avoidable efficiency defect, make the implementation change and compare the original and repaired versions under the same workload, memory conditions, initial state and accepted transaction boundaries. Retain both source identities and actual jobs, affected functional checks, whole-task/service results and any changed resource or clock assumptions. A changed estimate, diagnostic trace or proposed fix is not that repair.

Submit any claimed reasonable tradeoff for independent review with actual evidence, the considered alternatives and their feasibility or bounds, resource/clock budgets and residual risks. The reviewer must check the argument; implementation self-description is insufficient. A justified baseline may retain an unmet ideal target or unproven target feasibility, explicitly reported without claiming target met. It cannot waive a hard requirement or an established material avoidable defect. Reconcile changed architectural claims through the full revision path before returning the repair.

## Repair and return

Change the responsible RTL, data packing, initialization, scheduling or development test. Do not change the original acceptance threshold or remove a legal case. If an audit-owned test appears incorrect, report the source-backed discrepancy and a reproducer; the audit context decides whether to correct that test and retains its prior result. A genuine conflict between specification and reference is unresolved until an authorized source interpretation is available.

Use directed development checks to validate the fix and nearby boundaries. Rerun affected integration checks after modifying numeric behavior, state/control, interfaces or memory ordering. Synthesis follows the changed risk: use local structural/synthesis checks for changed datapaths or storage organization, and update whole-design evidence for the final relevant candidate. Adding a trace or changing only test stimuli does not by itself require a whole-design synthesis. Existing evidence is reusable only while its source, dependencies, configuration and tool conditions remain applicable.

For a changed resource or schedule, [measure the implemented schedule](../SKILL.md#measure-the-implemented-schedule) along the retained top transaction and use the observed service/cycle gap to choose the next focused check before repeating a long mapping run.

Before returning the repair, [reconcile the implemented baseline](architecture-revision.md#reconcile-the-implemented-baseline). Use the existing architecture revision interface for major resource, ABI, internal precision or budget changes. Ordinary implementation details remain within this repair. An unavailable architecture reviewer cannot confer approval, but does not prevent recording an implementation candidate and its unresolved conditions.

Update the plan and progress/handoff with the findings addressed, actual changes, commands and job IDs, remaining failures, and the new candidate's source fingerprints. Preserve failed runs. The independent audit must decide whether findings are closed and source acceptance is satisfied. If repeated attempts make no progress, tools are unavailable, or requirements conflict, hand off the concrete reproducer and blocking condition instead of changing rules or claiming completion.
