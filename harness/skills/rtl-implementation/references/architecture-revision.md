# Architecture revision during RTL implementation

This is a focused implementation-revision mode. The existing design/audit skill supplies engineering judgment; its full architecture-stage serialization protocol is used only by that stage. Here the current native tools and the following scoped handoff apply. Preserve the original source requirements. Historical frozen files remain unchanged.

Each native child receives the complete frozen caller task and its verified UTF-8 SHA before delegation begins. Optional skill text supplies engineering methods; the native role contract supplied after it governs tools, scoped evidence and persisted files. Use native `proposal`, `evaluate` and actual remote jobs rather than full-stage `check_proposal`, `recompute` or source-only receipt prerequisites. The native reviewer must write its scoped `review.json`; final prose or an `AUDIT_REPORT` frame is not publication. This operational boundary does not remove source obligations, actual recalculation, independent evidence, eligible adoption or parent readback.

Native design and review children write only in the supplied current writable scope or per-job temporary environment and use earlier evidence read-only. Before executing reused scripts or commands, inspect their output, build, cache and temporary paths; direct new products to the current scope instead of historical absolute output paths. A failed integrity check is not repaired by rewriting a frozen or decided identity or its evidence. Preserve the recorded and observed identities and return the unresolved condition for controlled recovery.

File paths and command working directories are scope-relative. The exact current run-relative scope prefix may be supplied once; a different scope is not writable. Use `./` to explicitly name a local subdirectory that resembles a run scope. Use the canonical `path`, `scope` and `run_path` returned by writes when referring to the result, and reuse paths returned by listings. All `@` aliases remain read-only. To publish the native architecture review, use the write action with `path: "review.json"` in the supplied audit scope, after reading any existing file for its version. Do not prepend the audit scope again or rely on final prose to publish the report.

The implementation agent requests a change with the actual failure, evidence paths and proposed impact. The caller creates a versioned candidate from the current architecture. Current work paths are supplied; read originals at @input/, prior architecture at @architecture/, and actual evidence at @run/. Keep estimates distinct from RTL results. Revise all affected representations, numeric widths, state lifetimes, supply/rates, storage, traffic, costs and prose together, without restarting unrelated architectural exploration.

The return includes the actual selected estimates and full budget-report path/hash, plus the adopted packet's paths and fingerprints. Read the new `@architecture/` baseline after adoption; its native review, scoped decision and provenance replace inherited approval records. The reviewed proposal and all earlier packets remain unchanged within this run. The original project handoff and frozen snapshot remain historical inputs; exporting a revision is a separate operation.

Keep the source-defined status of each constraint through the revision. Functional, numerical, protocol and explicit hard resource requirements are unchanged; a mandatory performance requirement cannot be waived by lowering an estimate. An ideal-target gap may be recorded as unmet or feasibility unproven without becoming a new hard gate. Revising the engineering baseline requires the complete revised packet, actual final recalculation, independent review of evidence and tradeoffs, versioned adoption and parent readback. An internally consistent recalculation alone neither proves target attainment nor replaces a required implementation efficiency repair.

## Reconcile the implemented baseline

Identify the actual selected packet and read its declarations and provenance before comparing the implementation. An imported packet can already contain adopted revisions. Earlier plans, revision comparison columns, a pointer status or an empty new-run revision directory do not establish the current representation or its adoption history. Cite the actual baseline file fingerprints and relevant declarations; distinguish the reviewed candidate's frozen packet from a subsequently changed run-current packet.

Before ending generation or repair, compare the actual RTL's numerical representations, resource/storage replication, interfaces, service rates and whole-task cycles/traffic with the current `@architecture/`, citing the actual source, job and current revision identities. State the consequential differences and whether they invalidate the current declarations or estimates. A material contradiction between measured service/task cost and the published model requires reconciliation even if the hardware organization has not changed; do not retain an invalid performance estimate as the current baseline. Keep measured scope distinct from estimates. Ordinary implementation refinements may remain local; a major deviation must go through `rtl_revise_architecture`, update the affected design declarations and prose together, and recalculate affected budgets, capacity and performance before treating the returned packet as a consistent current baseline. If this cannot be completed, retain the discrepancy as unresolved and do not attribute the parent's estimates or approval to the changed implementation. The audit makes this comparison independently from the implementation and actual evidence; an implementation self-report or an unchanged current pointer does not establish consistency.

After adoption, retrieve the returned current packet, including the revised architecture, design, changes, budget result, independent review and scoped decision. Inspect the changed commitments and their consequences before continuing implementation. Check read truncation and returned ranges, and retrieve missing portions before claiming complete coverage; line counts alone cannot prove a long line was delivered intact. Distinguish a complete downloadable packet from what the model actually inspected. A path, selected estimate or parent final statement alone does not prove complete handoff or readback.

The adopting implementation parent must complete this readback in that same session before ending generation or repair. Use the returned `readback_required_files` index: read every listed file at its canonical path and pinned version, including the complete architecture, design, changes, budgets, review, decision, provenance, budget binding and execution record. For each file, begin at its start and follow every `next_cursor` with the same path until `eof`; retain continuous byte coverage from zero through the stated size. Reaching an end page, jumping to the next numbered line after a truncated line, or reading only changed fields does not establish complete delivery. A source-version change requires a new complete read of that version. Do not count a child's or reviewer's reads as the parent's readback.

The controller records a body-free witness from that parent's actual successful tool returns after the session ends. Adoption and independent architecture approval remain separate from this witness. Check the returned packet now rather than assuming later RTL review can supply missing parent reads. The witness proves delivery of the required bytes, not understanding or engineering correctness; explain the consequential changes and verify the implementation independently. If complete readback cannot be obtained, report the concrete unresolved condition and preserve it; do not invent a receipt, substitute a different parent or repeat delegation solely to conceal missing evidence.

## Design role

Read the request and decisive original requirements/evidence. Edit candidate `design.json`, `architecture.md` and `CHANGES.md`; preserve requirements and unaffected candidates. Use the existing structured declarations and calculator references under @skill/microarchitecture-design/references/. Execute `evaluate` after changing design.json; it invokes the existing frozen budget engine on the server and returns actual candidate checks. Repair invalid declarations and real budget violations, rather than rewriting calculator outputs. Final prose must reflect the evaluated design. Keep unresolved implementation/physical conditions explicit. The caller repeats the final calculation before review.

## Review role

Your work scope is a separate audit directory. Read the complete source requirements and relevant reference code, old architecture, request, candidate and actual calculator report via @run/. Assess the change and its consequences independently; the implementation conversation is not supplied. Execute focused independent numeric, geometry, capacity or scheduling probes using the server tools when they decide the judgment. Record the actual job IDs and results. Evaluate checks against the updated proposal, not the old accepted report.

In this role, native `evaluate` reads the proposal and executes the frozen calculator into a new private audit calculation directory. Its returned report, execution and binding paths are independent evidence; it does not rewrite candidate budgets or replace the caller's final calculation. Read the returned artifacts and verify their proposal/design binding. The complete candidate fingerprint must remain unchanged through this verification and the independent probes. If it changes, earlier report or job bindings are stale; do not repair them by substituting the new fingerprint or moving an old report into place.

Write `review.json` in the audit scope with `verdict` (`accept`, `revise`, `insufficient_evidence`), `design_sha256` (the exact candidate file SHA returned by read), `candidate_sha256` (the complete candidate fingerprint returned by `proposal`), `reason`, `evidence` (actual successful independent job IDs) and `conditions`. Acceptance requires a successful fresh budget calculation when that capability exists, source-backed assessment of significant changed claims and independent executed evidence bound to these candidate bytes. Use `proposal` to retrieve the full candidate fingerprint before executing probes and writing review.json. Cite only actual relevant executed job IDs as positive evidence. A missing physical model may remain a condition; an actual source contradiction or violated hard budget needs revision. This scoped report authorizes implementation exploration; it is not a full architecture-stage acceptance or completed RTL validation.

## Optional capabilities

With no design skill, the implementation agent edits the candidate using this mode's responsibilities. With no audit skill, revision status remains `not_run`; implementation and verification may proceed without inheriting old approval. Actual failed checks cannot be bypassed as unavailable capabilities. Implement ordinary details directly. When a proposed fix would change original requirements, stop that proposal and describe the unresolved conflict.
