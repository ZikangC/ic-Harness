# RTL implementation

Deliver a substantive synthesizable RTL first version, necessary data exchange tools, implementation self-checks and a reproducible handoff. This is the generation stage: its self-checks support development and expose gaps; subsequent independent code review, acceptance and release are separate responsibilities. Do not label self-check success as independent verification or permission to release. Read the frozen specification, reference and accepted architecture first. Source requirements define behavior and acceptance; the architecture is a fallible implementation baseline. Extract project dimensions, operators, interfaces, legal parameters, precision and budgets from those inputs, never from generic harness defaults.

Identify the source and status of each constraint before making tradeoffs. Preserve functional, numerical, protocol and explicitly mandatory resource limits. A performance threshold is a hard gate only when the source requirements or explicit caller instruction make it mandatory; an ideal throughput or optimization estimate does not become one from the size of the gap. Record an unclear classification without promoting it to a hard gate. A request to repair efficiency requires addressing demonstrated defects, but does not by itself make every ideal target mandatory. Report an unmet target or unproven feasibility explicitly; never claim the target was met.

## Implementation plan

Use one implementation agent. Before substantial RTL, create a concise implementation plan mapping required computation, storage, control, initialization and outputs to the intended modules and their connections. For each module identify its role, resource/state ownership, interfaces, dependencies and useful self-check. Map these choices back to the source requirements and architecture; identify missing or conflicting assumptions. Choose the first runnable legal transaction and the resource/state boundaries along which it can be implemented in increments. Keep the plan proportional to the design and update it as implementation changes. A small cohesive design may use one RTL module. Do not mechanically make one module per source operator or split hardware according to the model's response size. Divide according to shared resources, state ownership, ports and timing. The plan guides the work; it does not redo the whole architecture stage.

Read the relevant specification and reference source directly, and cite their sections/functions for the external interface, arithmetic and state dependencies in the plan. Check `total_lines` in read results and retrieve the remaining relevant sections before claiming to have inspected them. Running the reference to generate expected outputs does not establish that these source requirements were inspected. Architecture prose alone is insufficient to define them.

Before connecting shared engines, memories and sequencers, make their implemented contracts explicit: operand address units, tensor/row/element meanings, numeric units and rounding boundaries, state ownership, accumulator lifetime, synchronous read latency, and the start/completion handshake. Generated schedules and RTL must use the same contract. Check a short transaction trace through the actual implementation before expanding the program; nominal operator order does not establish that the intended operands were read or that an operation executed exactly once.

## Implement and self-check together

Implement tightly coupled RTL and tests together, using a growing computation through the real top to choose the next work. Resolve organization-critical numeric or service questions with focused probes, then make a minimum task allowed by the original requirements runnable: supply its initialization and operands through the supported external input/storage interfaces, execute its required computation and state dependencies, and observe its outputs and completion. Reduce the case's data/configuration scope while retaining the stages needed to produce that result. Choose legal stimulus that distinguishes plausible mistakes and compare independently derived intermediate results to find the first broken producer/consumer boundary and implement its owning resource next.

For a larger design, grow this path in increments that share an engine, storage owner or control sequence. Connect and exercise each increment with the retained result of its producer; this makes leaf checks and interface work serve the same integration attempt. Temporary scaffolding can support construction, but an unimplemented executor or bypassed computation leaves that path unfinished. Once the minimum required chain works, expand the remaining paths and legal configurations. Drive this loop yourself using the supplied tools; do not depend on an external operator finding each defect, supplying project-specific repair hints or repeatedly restarting an otherwise unblocked session. Local unit success does not establish system correctness.

Prioritize decisions capable of invalidating the organization: numeric precision and discrete selection, wide reductions and small constants, state update/read dependencies, actual operand supply, nonlinear latency/service, initialization and output completion. Numerical proxies can guide choices; distinguish them from actual RTL execution. Expected outputs come from the frozen source reference or independent calculations. Preserve failed evidence and correct a test only with a source-backed explanation.

Choose small directed RTL checks that distinguish plausible implementation mistakes before a broad end-to-end debug run. Derive intermediate units independently rather than copying the DUT's shifts or index expressions into the oracle. Asymmetric nonzero operands help distinguish axis/order errors; multi-phase checks must demonstrate that a consumer uses the producer's retained result. Exercise the last legal element and the transaction completion boundary. A test must reject stalls, timeouts, missing outputs and missing completion, rather than continue and score an incomplete dump. Read the test's actual verdict and counts even when its process exits normally.

Complete compute, storage, memory control, initialization, output and top integration. Software, DPI, real-valued simulation arithmetic, preset weights/results and synthesis-only black boxes cannot replace required computation. Reusable helpers must remain independent of this project. Project-specific RTL, packers, testbenches, datasets and reports belong in the current run.

Derive self-check coverage from every original functional, numeric and interface requirement: legal runtime parameters, sequence/state boundaries, variable memory latency/backpressure, subsequent tasks without reset, initialization independence, output completeness/order, address geometry and byte enables. Execute the checks relevant to the delivered first version and identify unexecuted or failed coverage explicitly. Check elaboration and synthesis compatibility. Count actual storage instances/replication and report measured cycle scope. Keep estimates, local synthesis and full design results separate. Report absent physical conditions explicitly; a measured violation remains a violation even when other physical conditions are unavailable.

Before a first-version handoff, a completed repair or a long whole-design mapping run, record the complete delivery configurations in the source-root `RTL_STRUCTURE.json` compile declaration and execute the [structural preflight](references/repair.md#structural-preflight-and-diagnostic-disposition) for the complete delivered compilation configuration. Use the native `rtl_remote` `structure_check` action with explicit `execution_plan: "diagnostic_first"` for early full-configuration lint diagnosis. Completed lint target findings return complete negative evidence before Yosys; inspect the original diagnostics, classify the implicated use, repair actual defects and confirm terminal cleanup before editing. Submit a new check for the repaired source. Lint clean still continues through the existing complete path. For final evidence or an independently justified diagnostic disposition, request `execution_plan: "complete"`; it retains both trusted stages and the existing release requirements. Omission also retains that complete path. A diagnostic-only return leaves bitwise coverage unclosed and cannot establish structural acceptance; completing whole-design Yosys every debug round is not the goal. A separate development lint is optional supporting evidence, not a required duplicate invocation or a replacement for the native stages. Inspect real-time logs and the actual terminal result, rather than waiting for an expensive frontend without using available diagnostics. A leaf-only check, successful lint exit, sample simulation or local two-state equivalence does not establish that the delivered top has no used undriven bits. Unexecuted, unsupported, timed-out or source-stale checks remain open; do not mark the implementation structurally checked or the handoff complete on that basis. Preserve failed diagnostics and fix the responsible RTL through the normal implementation path. A tool failure, cancellation or incomplete check remains blocked/open; ending a model session or increasing a timeout does not complete an RTL repair.

Before queueing a source-bound native check, stop other writers and generating jobs for its complete bound scope closure; while queued or running, do not edit RTL, the compile declaration, PROGRESS, tests or other closure files. Read and analyze existing evidence while waiting; edit only after completion or safe cancellation with confirmed terminal cleanup, then submit a new check for the new source identity. A changed closure invalidates the old evidence; do not refresh or retry its old expected fingerprint.

### Measure the implemented schedule

As a legal top transaction becomes executable, use a representative repeated window to compare budgeted service with actual accepted reads, operand readiness, useful issues and committed writes. Count useful work over elapsed cycles, including idle/stall cycles; distinguish operation latency from the interval between successive accepted operations. Trace lost issue opportunities to their fetch, compute or commit owner and dependencies. Lane count and peak issue rate do not establish sustained utilization. Keep instrumentation observational and functional failures visible.

Use the source workload and implemented resource/port/issue capabilities to bound whole-task cycles, adding required serial phases and crediting only justified overlap. Compare that bound with representative measured task cycles under the same boundary: show initialization, input, compute and output/completion, separating one-time setup from recurring work only when the source permits reuse. Explain extrapolation and unmeasured tails instead of extending a short steady-state rate to the entire task. Feed changed service, traffic or cycle assumptions through the existing architecture revision and recalculation path when they materially change the baseline.

Use the prescribed workload, memory conditions and accepted transaction edges for an acceptance measurement. A queued command, driver start, reduced stress case or warm repeated task is not interchangeable with the required boundary or initial state. Retain configuration, source and job identities for each comparison. Report incomplete output or protocol failures before a numerical score or performance ratio.

When the task requests an efficiency repair, use a measured discrepancy to choose a consequential owning boundary and test its explanation. A material avoidable efficiency defect established by actual evidence requires a real implementation repair and matched before/after verification of service and whole-task cost, with affected functional checks and resource/clock consequences. Analysis, instrumentation, a proposed optimization or revised estimates alone do not complete that repair. A gap from an ideal target alone does not establish an avoidable defect. If the hypothesis is refuted, use that observation to choose the next investigation; if the repair remains unfinished, preserve its reproducer and state that explicitly. Any claim that the remaining cost is a reasonable tradeoff needs the independent assessment described in [repair.md](references/repair.md#efficiency-repairs-and-tradeoffs).

Before a long whole-design mapping run, use this comparison to choose the unresolved question it can answer. A large schedule/service gap needs evidence at its owning boundary; mapping unchanged unrelated logic cannot explain it. When service assumes a long combinational operation, inspect the actual register boundaries and obtain focused structural/synthesis or timing evidence with available models and constraints early. Cycle simulation does not establish achievable clock frequency; missing physical evidence remains explicit. This selects useful development work without replacing required final synthesis or source acceptance checks.

When a check fails, diagnose the actual failure and modify the responsible artifact; do not relax the source gates. After changing a path, rerun its affected checks against the final source; bind each result to source fingerprints and job IDs so old passing evidence is not attributed to new code. When no progress follows repeated equivalent attempts, preserve a concrete reproducer and report the unresolved condition.

Keep `PROGRESS.md` current with implemented modules/interfaces, decisions, commands, passing/failing checks and the next task. At a useful integration increment or as the context becomes crowded, make it a recoverable checkpoint: retain the runnable case, unfinished boundary and next concrete edit with the relevant source/job identities. Keep long traces on the server and summarize older exploration so the next work can start from that checkpoint. Use available context compaction or resume support to continue. Report a caller/runtime limit only when one is actually supplied or observed; if it forces a handoff, identify the incomplete implementation and exact next action. A checkpoint does not complete a missing computation or integration milestone.

## First-version handoff

The controller explicitly selects this skill for ordinary RTL generation and any implementation repair. It owns routing, persistent repair budgets, lifecycle and recovery. An audit report alone does not select this executor; a candidate created by Readiness returns to Readiness when that caller selects it. This skill returns its candidate and evidence without starting independent audit itself.

A completed first version requires substantive implementation of all required paths and top connections; successful compilation/elaboration of the final source; completed source-bound structural preflight and applicable synthesis-compatibility checks with available tools; executed directed self-checks of the key risks; and at least one minimum legal case that passes its applicable output and completion checks through the actual top. Testbench-supplied computation or direct internal-memory injection does not establish an external input/output path. Do not label a skeleton, missing required computation, failing minimum case or unexecuted integration as completed. Such work may be handed off explicitly as an incomplete implementation with its reproducer and next step.

Deliver the plan, RTL and necessary tools, self-check results and coverage gaps, unresolved issues, input/architecture/source fingerprints and reproducible commands. Distinguish this initial implementation milestone from full requirement coverage. State that downstream independent review and acceptance have not been performed by this generation skill. Do not conclude correctness from generated file presence or successful tool exit codes alone.

Before this handoff, [reconcile the implemented baseline](references/architecture-revision.md#reconcile-the-implemented-baseline), including any major departure that requires architecture revision and recalculation.

## Revision mode

When called with an independent audit report, use this skill to diagnose and repair the existing implementation rather than regenerate it from scratch. Read [repair.md](references/repair.md). The report supplies failures and evidence, not necessarily the root cause; use the tools to investigate and make progress without project-specific guidance from an external operator. Keep audit-owned tests and the frozen candidate unchanged. Deliver a revised implementation and development evidence for a fresh independent review; closing your own repair does not close the audit finding.

## Tools and architecture feedback

The registered remote tools operate exclusively on the server run. Use `rtl_remote` to list/read, write with a matching base SHA, replace one exact text span, submit commands and query jobs. New files use `base_sha256:null`. Paths default to the current work directory. Read aliases are `@input/`, `@architecture/`, `@skill/`, `@run/`; they also work in directory queries and command arguments. Execution of an input alias uses the frozen physical source layout so declared support imports remain valid. Available executable aliases and actual remote paths are supplied by the caller. Commands use argv arrays; write a server-side Python script when composition is needed. Submit returns a persistent job ID. Query it, inspect small diagnostics and perform other useful work while it runs. Large binaries, data, waveforms and complete logs stay on the server. Never launch a duplicate job because an SSH response was delayed; inspect the existing jobs first.

Treat frozen inputs, candidates and prior evidence as read-only, including indirect writes by invoked tools. Before reusing a script or command, inspect its output, build, cache and temporary paths; direct new products to the supplied current writable scope or per-job temporary environment instead of retaining historical absolute output paths. Reuse prior artifacts by reference after checking applicability; reruns produce new scoped artifacts. An integrity mismatch must preserve the recorded and observed identities. Do not replace a frozen or decided fingerprint or its evidence to make a guard pass; report the mismatch for controlled recovery.

For a complete file read, inspect `truncated` and follow `next_cursor` with the same `path` using `cursor` until `eof`. Exact `content` and returned byte ranges include long-line continuations; numbered `text` is a display view. Do not skip a truncated line by advancing its line number or claim complete coverage from `total_lines` alone. A changed source invalidates its cursor and needs a new read.

Record significant architecture assumptions in the implementation plan before writing their dependent RTL. Ordinary pipelining, local control, tails and addresses can be refined directly. Major changes to resources, ABI, internal precision or budget go through `rtl_revise_architecture` with real evidence and an explicit proposal; read [architecture-revision.md](references/architecture-revision.md) when using that interface. Optional architecture skills improve the judgment but are not prerequisites for RTL startup. Missing review is recorded, never converted into acceptance. A known failed mandatory requirement or hard budget remains a failure; an ideal-target gap keeps its source-defined status and cannot be hidden by recalculating the baseline.

After an adopted revision returns, this same implementation session must read all files in its `readback_required_files` index at the returned version before ending. Follow byte-bound `next_cursor` pages without gaps, including complete design and budget JSON; a summary, final page or delegate completion cannot replace the parent readback. The controller's later witness records actual tool exposure, separately from adoption and engineering validation.
