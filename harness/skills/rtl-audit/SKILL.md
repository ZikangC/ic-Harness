# RTL audit

Review the actual frozen implementation, not its author's confidence. This skill independently checks one candidate and owns its engineering conclusion. The caller supplies the candidate identity, source requirements, accepted architecture, delivery objective and review scope. It receives the report and chooses any repair executor, candidate freezing and subsequent review; this skill neither edits RTL nor launches that repair loop. A later candidate requires a fresh independent audit context. No implementation or orchestration skill is required to complete this review. Do not rely on an external operator to find defects or guide each check.

## Establish the review basis

Read the frozen specification and relevant reference source, accepted architecture, current review scope and candidate identity. Source requirements define functional, numerical and interface acceptance; architecture prose is a fallible implementation baseline. Inspect the relevant remaining sections before citing them. With a cursor-based file adapter, follow `next_cursor` with the same `path` using `cursor` until `eof`, checking `truncated` and exact `content` byte ranges; `total_lines` alone cannot prove a long line was delivered intact. With ordinary file tools, likewise resolve truncation before claiming a complete read. Executing a reference is not evidence that its source requirements were inspected. Resolve project dimensions, legal parameters, thresholds, interfaces and precision from these sources, never generic defaults.

Inspect the actual top, connected computation, state/storage, initialization, data packing and output/completion paths. Reject required paths implemented only as stubs, constants, testbench computation, DPI/software callbacks or synthesis black boxes. A file list, module names, successful elaboration or a generated report alone does not establish a working implementation.

Build a concise source-to-evidence account of the acceptance obligations. Cover every legal runtime parameter class and required numerical criterion, including accuracy, discrete selections such as argmax, permitted error metrics and their specified aggregation. Preserve prescribed datasets and evaluation procedures; a smaller development case cannot substitute for the required acceptance workload. Inspect state sequencing, boundaries, variable latency/backpressure, repeated runs, initialization and ABI/address/tail behavior where applicable. Derive relevant obligations from this project instead of using a fixed operator checklist.

For each aggregate, retain its exact case population, numerator and denominator, and reconcile the reported value with the source's required grouping. Keep exploratory or boundary cases separate when the source does not include them in that acceptance population. State which expected fields and cases were independently checked; matching a selection field alone does not verify the complete numerical oracle.

Classify each resource or performance condition from the original requirements and the caller's actual delivery instruction, citing its source. Preserve functional, numerical, protocol and explicitly mandatory resource gates. A performance threshold is mandatory only when those sources establish it as a hard requirement. Architecture estimates and ideal optimization targets do not introduce extra gates; an unclear classification must be reported without automatically promoting it to a hard gate. Report measured resources, cycles and physical limitations separately. Do not discard explicit source constraints or claim unavailable area/timing evidence; full physical closure requires its actual models and conditions. If an essential acceptance obligation cannot be checked, report insufficient evidence rather than relabeling it passed.

An explicit objective to repair execution efficiency requires investigation and actual repair of a material avoidable defect established by evidence. Keep such a defect open with `revise` until the implementation change and matched before/after verification are independently checked; use `insufficient_evidence` when the decisive evidence is unavailable. A functional sub-pass, instrumentation, a proposal or revised estimates alone cannot close it. A gap from an ideal throughput target alone does not establish an avoidable defect or make that target mandatory; do not invent a universal utilization threshold.

Independently assess a claimed reasonable tradeoff from actual service/whole-task results, plausible alternatives and their demonstrated or bounded feasibility, resource and clock budgets, and residual risks. An implementation self-description or unexplored assertion that improvement is impossible is insufficient. Distinguish a demonstrated unavoidable cost, a justified engineering choice and an unresolved hypothesis. Missing physical evidence limits any claim of achievable clock or throughput.

An unmet ideal target alone must not force an overall failure. A candidate may be accepted as an engineering baseline when the mandatory obligations and actual delivery objectives are satisfied and the remaining tradeoff has adequate independent support. State the target as unmet or feasibility as unproven, with the measured baseline and limits; never label it target met. A verified hard performance violation or material avoidable defect remains an open finding.

Read the architecture packet bound to the supplied frozen candidate, including its design declarations, narrative and available revision provenance. In a native harness run, also read `@run/architecture-current.json` and distinguish any later run-current change from the candidate's baseline. An imported baseline may already contain adopted revisions: inspect the source/adoption records and their scope. A pointer status or the absence of a new revision directory alone proves neither a material deviation nor missing adoption. Planning notes, old revision values and comparison columns do not replace the selected packet's current declarations.

Before asserting an architecture mismatch, cite the actual candidate evidence and the conflicting declaration in the identified packet, with file/version fingerprints and the relevant field or text range. If that comparison has not been inspected, state the unverified question rather than asserting the old value. Distinguish an actual new resource, ABI or internal-precision change whose required review is missing or unsuccessful; it cannot inherit the old architecture's approval. Optional design/review capabilities may be absent while an implementation candidate is produced, but missing required change evidence cannot support a pass.

Independently reconcile the actual RTL's numerical representations, resource/storage replication, interfaces, sustained service and whole-task cycles/traffic with that architecture packet and source-bound jobs. Identify consequential differences and whether they invalidate its declarations or estimates. A material measured service/task-cost contradiction requires reconciliation even when hardware organization is unchanged. Major deviations require updated affected declarations and prose, recalculated budgets/capacity/performance, and applicable independent architecture review. Report unresolved changes to the caller; do not launch architecture revision from this audit. A self-reported match or unchanged architecture pointer does not close a material deviation or supply its missing recalculation and review.

For a native revision requiring parent readback, inspect the supplied frozen architecture identity's `parent_readback` evidence. Require a complete controller witness bound to that exact baseline, handoff and adopting implementation session, backed by the actual successful tool returns and completed isolated session. An adopted pointer, complete files on disk, architecture-child review or your own reads do not prove the parent's complete delivery. This witness establishes byte exposure only; still assess the changed commitments independently. Missing or incomplete original-parent evidence cannot support `pass`. If that parent has already ended and the evidence cannot be completed in its session, report the concrete capability/evidence block instead of asking new repair sessions to impersonate it or indefinitely repeating the same handoff. Do not add this native-revision obligation to an unchanged original snapshot without a revision.

## Execute independent checks

Keep tests and expected-result derivation independent of the DUT's arithmetic and indexing. Read the frozen reference or derive expected values from source rules; do not use DUT outputs as an oracle. Existing implementation checks are useful evidence to inspect, not the sole basis for acceptance. Exercise the actual external top path and reject incomplete output, stalls, timeouts, missing completion and scoring only a successful subset. Distinguish simulation/proxy results, local synthesis and full-design results.

Use fast lint/elaboration and focused simulation while investigating. Perform local synthesis when datapath, storage, sharing or service-rate assumptions need evidence, and whole-design synthesis for a relevant final candidate. Do not repeat an expensive run solely to make it independent: inspect and reuse actual source-bound jobs when their scope, dependencies, parameters, tool version and conditions still apply. Changed relevant source or conditions invalidate that evidence. Check logs and result counts, not just process exit status or another model's summary.

Independently check the implemented schedule evidence: reconcile actual accepted reads, operand readiness, useful issues and committed writes over elapsed cycles, including stalls, with the current service budget. Distinguish operation latency from issue interval and peak lane count from sustained useful service. Bound whole-task cost from the prescribed workload and actual resource/port/issue limits, adding required serial phases and crediting only justified overlap. Compare representative measured cycles under the same boundaries, separating one-time setup only where the source permits reuse and explaining extrapolation and unmeasured tails. A short steady-state rate or an implementation summary cannot establish full-task performance; missing clock/library evidence cannot become a timing claim. Use a discrepancy to select the next decisive check or finding.

Verify the workload, memory profile, initial/repeated-task state and actual accepted measurement boundaries before comparing performance. For a requested repair, inspect the implemented change and matched before/after evidence, including affected functional checks and resource/timing consequences. Unchanged cost or an unimplemented proposal is not evidence of efficiency repair. A structural timing risk calls for relevant register/path and focused timing evidence; a large design's mapping duration alone neither proves the RTL cause nor closes that risk.

Retain the actual accepted-start and completion event markers used by the counter. If a driver counter includes configuration, queueing, polling or extra edges, identify that scope and bound the difference before using it as the source-defined metric. A clear measured violation may remain decisive, but an inexact boundary must not be presented as exact acceptance evidence.

The report's `evidence` array accepts only actual jobs in this audit scope bound to this candidate. Cite implementation or prior-review jobs as supporting material; execute a current audit verification to check their applicable dependencies, parameters, tool conditions and actual results. With the native job adapter, retain that verification's job ID; without it, retain the command, result and source/tool/configuration identities as supporting material without inventing a job ID. That verification need not repeat the expensive synthesis itself.

Evidence reuse is read-only. Inspect reused scripts and configuration for indirect writes and historical absolute output paths before execution; place new verification products in the supplied current writable scope or per-job temporary environment. A current verification job checks applicability and actual results without updating the cited old outputs, receipts or decided report. If their integrity guard fails, preserve the recorded and observed identities and report the discrepancy; do not refresh their frozen or decided fingerprints to make the guard pass.

When acceptance fails, read [debug.md](references/debug.md). Produce a reproducible finding and enough evidence for the caller's chosen repair executor to investigate; the audit need not finish all root-cause analysis before returning `revise`. Keep audit-owned tests separate from candidate modification work. Correct a faulty audit test only from the original requirements, retaining the prior test/result and explaining the correction. Never lower acceptance thresholds to fit the current RTL.

## Report and conclude

Separate observed acceptance failures from localization hypotheses. Attribute a failure to a particular stage or state mechanism only with evidence that isolates it, such as an independently checked local contract using the actual operands/state or a source-backed counterexample. End-to-end scores and position trends alone do not identify that cause. Otherwise label the hypothesis and the observation needed to distinguish it. Do not prescribe a patch unsupported by evidence.

Write a JSON review report in the current audit work scope. Required fields are:

```json
{
  "verdict": "revise",
  "candidate_sha256": "<exact identity supplied for this candidate>",
  "reason": "<source-backed conclusion and actionable findings>",
  "evidence": ["<actual relevant remote job ID>"]
}
```

Use `pass`, `revise`, `insufficient_evidence` or `blocked` for `verdict`. Add finding locations, source obligations and their hard-gate or ideal-target status, commands, expected/actual results, unresolved conditions and coverage detail as needed; do not manufacture empty fields or jobs. `pass` requires the current candidate to satisfy the applicable source acceptance obligations and explicit delivery objectives, classified as above, with adequate actual execution evidence. An implementation self-check or an old candidate's result cannot authorize it. `revise` identifies implementation defects that can be worked on. `insufficient_evidence` identifies an undecided obligation or source conflict; `blocked` identifies a concrete environmental/capability condition preventing useful progress. None of the latter outcomes is permission to release.

Save the report and return its path, verdict and candidate identity, then end this review. The caller decides whether to release, obtain missing evidence, request an architecture revision or send findings to a repair executor; the review does not choose that executor or start another candidate's review. Do not edit RTL in the audit scope or continue judging a candidate while it is being revised.

If the caller provides native publication tools, use `rtl_request_revision({"report_path":"<audit-relative report path>"})` for `revise`, or `rtl_finish_review({"report_path":"<audit-relative report path>"})` for the other verdicts. These tools persist this candidate-bound outcome for the caller; publication is not permission for this skill to launch a repair. Inspect a failed publication's diagnostic and preserve the report rather than claiming a completed handoff. Without those tools, the saved report is the review deliverable. Preserve failures and unresolved evidence. Repeated equivalent attempts without progress must finish with the concrete remaining condition; do not loop indefinitely or convert missing capabilities into a pass. Runtime review does not modify generic skills, controller code or original requirements.

## Tool and artifact boundaries

Use the caller's available file and execution tools, keeping candidate/source inputs read-only and new tests, logs and reports in the supplied audit work scope. When the native `rtl_remote` adapter is present, use it for directory/read operations, evidence/test files, persistent job submission and job status. Its `@candidate/` exposes the frozen implementation; `@input/`, `@architecture/`, `@skill/` and `@run/` are read-only. Follow the supplied executable aliases and remote paths. Adapter commands use argv arrays; use a server-side script when composition is needed. New adapter files use `base_sha256:null`; edits use the returned base SHA. Native review jobs are automatically bound to the supplied candidate identity; with other tools retain that identity with the executed configuration and results. Reference only real relevant job IDs in the report.

Large data, snapshots, waveforms and full logs stay on the server. Read small diagnostics and summaries. Inspect existing jobs after a delayed connection before submitting a duplicate. Preserve audit tests and past candidates for reproducibility, and report source/configuration/tool fingerprints with reusable evidence.
