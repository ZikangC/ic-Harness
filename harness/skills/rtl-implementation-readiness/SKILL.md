# RTL implementation readiness

Reduce the time from an RTL problem to a verified candidate and the next useful synthesis result. This skill investigates code whose synthesis behavior cannot be settled by reading alone: procedural expansion, repeated arithmetic, sharing versus replication, memory inference and deep selection logic. It can keep the original RTL when experiments show no worthwhile benefit.

Choose the change boundary by hardware responsibility and observable behavior, not the current function boundary or number of edited files. A useful candidate may extract a datapath from control, regroup writeback, or separate executor state from scheduling. Within a selected responsibility, inspect the relevant implementations and callers, their operand selection and control overlap before choosing a change. Existing reuse in one path does not establish coverage of the other paths. Select a candidate from those dependencies and cost evidence; a synthesis log alone does not establish a refactoring or its benefit. This focused investigation need not enumerate every optimization in the design.

Operate independently. Use your own reasoning and basic file tools to inspect RTL and create changes; the bundled Python helpers freeze inputs, run experiments and compare evidence. No implementation, review, architecture skill, project adapter, model-command service or parent-directory runtime is required. Those are optional downstream consumers.

Standalone completion may deliver an unreviewed candidate and its actual evidence. In this project, formally adopting modified RTL still requires the applicable independent RTL audit; that delivery requirement does not make another skill a prerequisite for diagnosis, experiments, comparison or candidate modification. The controller selects any downstream review and, for a Readiness-origin repair loop, explicitly routes candidate changes back to Readiness. An independent audit pass ends that review loop in the controller; it does not require another Readiness session for formal closeout.

## Choose diagnosis or optimization

Use **read-only diagnosis** when asked to investigate existing evidence. Use **experiment optimization** only when the caller authorizes that work with sufficient budget and resources. These may run in separate model sessions using ordinary reports; neither mode requires another skill or a controller. With basic file and execution tools, gather the same material directly and keep diagnosis commands read-only.

An RTL review pass, completed synthesis stage, exceeded caller-configured observation budget or job failure is an opportunity to look, not a verdict that the RTL is defective. A controller owns observation triggers, execution budgets, resource admission and duplicate-work prevention. This skill owns evidence applicability, engineering hypotheses, experiment choice and interpretation. Do not encode a project function, synthesis-pass name or fixed waiting period as a universal defect rule.

## Read-only diagnosis

Start from the caller's small material index, or build an equivalent inventory yourself: frozen source identity/location, ordered source/dependency list, top/parameters/defines, architecture/requirements, tools/libraries/constraints, existing job identities and state, and log/report paths. Select the material worth reading; avoid loading all source or large logs indiscriminately. Preserve source and observation timestamps. A snapshot describes its capture point; it cannot establish later completion.

Read existing evidence before recommending new tool work. Check which source/configuration/tool/stage each historical result covers, distinguish actual process identity from a stale PID, and separate observed runtime facts from explanations. A returned page or clipped excerpt is not the end of its source file: use range/continuation information to reach the decision-relevant evidence, and reconcile terminal messages with job records where available before claiming truncation, failure or completion. Retain uncertainty when lifecycle evidence is missing. Targeted reads suffice; do not read an entire large log merely to reach its ending. A quiet log alone does not prove a stuck job; rising CPU alone does not prove useful progress or completion. Missing mapping/clock/library evidence remains missing. Do not manufacture restart, mapping or STA support.

Turn a selected observation into a specific question before choosing a probe. Identify competing implementations or explanations and what a measurement or functional check would distinguish. A full-design frontend or system regression time, including a timeout, is not a lower bound for every useful local experiment. Exact source-linked widths, control, multiplicity and observable semantics can make a bounded local comparison representative of a mechanism without proving whole-design benefit. Consider that scope before requiring a whole-design pilot or declaring all local work unrepresentative. Keep its conclusions within that scope.

Form a concise ordinary report with `advice` (`continue`, `small_experiment` or `more_evidence`), `summary`, and `findings`. Bind each important finding to source/configuration identity and a readable evidence path/range; mark observation, inference and uncertainty. Apply the [investigation workflow](#investigate-important-findings) to material findings before recommending an action. Include an optional `experiments` list with the question, representative scope, functional obligation and proposed bounded cost. If evidence is sufficient, recommend the next useful action directly. If evidence is insufficient, request specific missing material or a small bounded probe; do not launch it from diagnosis. Do not modify RTL, submit/cancel jobs, publish an RTL verdict or use an optimization handoff in this mode. End normally with the report, even when the answer is incomplete.

The controller can retain a report and reuse it while meaningful evidence is unchanged. Its decision to authorize an experiment is separate from this advice. No new full-design synthesis follows automatically from a diagnosis, variant or local improvement. When authorized, pass the ordinary report into the existing experiment workflow below; the experiment model should check applicability again rather than treating a proposed cause or edit as established.

## Establish the scope

Read applicable project instructions and inspect user changes. Identify the actual synthesis top, ordered sources, generated headers, parameters, defines, memories and models. Inspect active jobs and available resources before starting work; do not cancel, upgrade or duplicate them. Existing job records must be checked against actual process identity and source/tool/configuration identities before reuse.

Keep the supplied candidate unchanged. Create all probes, variants, logs and exports in a new run directory on the authorized EDA machine. Respect the user's data-location rules. Do not launch a full design synthesis as the default experiment. If the supplied RTL is frozen or independently reviewed, candidate changes are proposals until the project's applicable integration/review steps are completed.

Before cost experiments, inspect applicable baseline structural evidence: source/dependency closure, build configuration, tool and actual completed check scope. Reuse existing results first; fill material gaps with bounded checks only when needed and affordable. Record known problems and unexamined scope rather than requiring a new full-design synthesis for each local experiment. After changing RTL, repeat an applicable check for the candidate. An elaboration pass, custom-command exit zero, timeout or incomplete check does not establish structural health. See [structural evidence](references/structural-health.md) for the read-only `health` helper and historical evidence interface.

If applicable lint or frontend structure evidence is missing or stale, select an affordable check with the project's available tools before assuming a clean baseline. Record the checks actually performed and their limits; an unavailable or unaffordable check leaves that scope unknown.

Use `scripts/readiness.py` (Python 3.10+, standard library) for the standalone workflow. Read [the command guide](references/commands.md) when invoking it. Explicit sources and literal include/readmem dependencies are snapshotted and hashed; include generated inputs and verification scripts/data as assets. Missing or unsupported dependencies require a smaller explicit scope or the actual frontend, never fabricated models.

Use the original source root as the default `--project` and preserve original relative paths and baseline hashes. A staging project can add frozen probe wrappers or test assets around exact original copies. Explicitly restrict editable paths so these verification inputs remain frozen; tests are not optimization targets. Do not add a run/output-directory prefix to integration paths. A separately extracted probe without matching original paths/bytes remains probe evidence until a corresponding source-bound integration candidate is verified.

For changes that create or remove RTL files or change the source list, opt into a regional workspace. Read [regional candidates](references/regional.md) for the actual helper interface, supported filelist format and immutable build identities. A new hardware module is a candidate source, not a frozen test wrapper. Keep simple existing-file overlays available for small edits.

## Investigate important findings

Build a compact triage of the material diagnostic set before spending most of the investigation budget on detailed traces. Use raw messages and source locations to group repetitions by likely mechanism and affected source region; one warning code can contain several distinct questions. Identify which groups are explained by applicable evidence and which could still change the decision. Select investigations from that overview, retaining unexamined groups and their locations for continuation. Do not let deep explanations of a few familiar examples replace this initial coverage assessment. This is triage, not a requirement to prove or individually explain every message.

After collecting tool evidence, investigate unresolved findings that could change the current correctness, cost or integration decision. Group related diagnostics and choose representative source locations by their likely significance and coverage gaps. Counts, severity labels and exit codes are an inventory, not a root-cause explanation. Do not dismiss an entire category after inspecting unrelated examples, or require every warning to become a defect investigation.

Trace a selected finding from its raw evidence into the relevant source, build settings, models or constraints. Follow producers, consumers and control where needed to explain the mechanism; compare the relevant paths rather than inferring a complete restructuring from one helper or module. Distinguish the reported symptom, its supported cause or competing hypotheses, and any unproved functional impact. Prefer existing evidence and source reasoning; when these cannot distinguish the hypotheses, identify the smallest discriminating check. Execute it only in an authorized experiment session and within budget. Resolve uncertainty that affects the interpretation of a planned experiment, or explicitly limit its claim. An unrelated local pass cannot close the original finding.

A diagnostic probe must preserve the source behavior relevant to its question. Normalizing inputs, supplying defaults, changing widths or exposing new outputs can hide or manufacture the condition being investigated; disclose any abstraction and limit the claim to what it preserves. Bind the probe to the original source spans and configuration. A probe-only observation is not proof of the original consumer's reachability or whole-design impact.

Report a supported explanation and its evidence, or a testable hypothesis with the specific missing check. Keep unexamined material findings and budget limits visible. Root-cause investigation does not require explaining every message or proving the whole design. Known or unresolved problems may accompany a scoped proposal or an explicitly authorized cost experiment; they cannot support a broader readiness or acceptance claim. Use ordinary findings and existing job receipts, without requiring another skill, report vocabulary or controller stage.

## Find an experiment worth running

Reuse an applicable diagnosis first. If needed, run `analyze`, then read the relevant source and logs. Its lexical observations are hypotheses, not a SystemVerilog parser, elapsed-time profiler or hardware census. Function-call counts are not physical instance counts. Code reuse often expands during lowering; later optimizations may recover sharing. Neither inlining nor a large loop alone proves a defect.

Choose the smallest scope that preserves the suspected mechanism: the real parameter/width/mode, clock/reset behavior, output observability, representative call multiplicity and required surrounding control. A wrapper that removes the actual cause does not answer the question. Inspect existing passes/checkpoints before rerunning earlier work, but do not claim generic tool support for restart: a saved checkpoint is reusable only when its source, options, tool and pass boundary match.

For regional changes, retain the relevant controller, callers and state interactions in the measurement or explicitly separate a smaller mechanism experiment from the region-level result. A fast function-only probe cannot certify that moving logic out of a large process made that process faster. Bound tool cost and hypotheses; do not force the candidate into a few lines merely to fit the old probe shape.

A smaller hierarchy top with the full source list can still incur expensive frontend work: the reader may parse or process unused modules before hierarchy pruning. Inspect the ordered sources as well as the selected top. Use the necessary source/dependency closure, or an extracted probe tied to exact original source spans, while retaining the mechanism under investigation. A top-name change alone does not establish a smaller experiment.

State a concrete hypothesis, measured stage and stopping budget before a probe. Start with elaboration or `proc` when lowering dominates; use generic synthesis only when gate/resource shape matters. The built-in stages do not perform technology mapping or STA. For another frontend/tool, use a bounded `command` with explicit dependencies and inspect its actual output.

Use a small campaign budget, typically two alternatives and a few short trials; adjust to the user's machine and task. For a candidate comparison, choose and justify the measurement/repetition strategy first (three baseline and three candidate measurements by default). Reserve jobs/time and delivery capacity for its still-missing measurements, paired functional check, comparison/export and required independent review before exploration. Reuse completed measurements or pilots with matching source/scope/configuration/tool identities after verifying their receipts; do not reserve duplicate tool work. If affordability is unestablished, use a short baseline pilot from a small fraction of the remaining exploratory budget; the per-job cap is a ceiling, not its target. Budget baseline-only diagnostic checks for their own checks and reporting.

If the pilot times out and the remaining budget covers a representative retry plus the selected completion work, narrow independent repetition/multiplicity and/or the source/dependency closure once. Remove work before the observed bottleneck: changing only a later stage over the same expensive inputs does not narrow that prerequisite. Preserve actual widths, modes, clock/reset/control, output observability and the suspected mechanism; reducing the scope must not erase the cause being measured. Establish an affordable baseline for the selected comparison scope from applicable completed evidence or a pilot before sealing an optimization variant or searching alternatives. A first timeout alone is not a stopping condition when that bounded narrower attempt still fits. Base a stopping decision on the remaining budget and chosen measurement/verification strategy; a timeout establishes only an incomplete observation for its actual scope. Stop honestly when a smaller probe would be unrepresentative, the narrower attempt remains unaffordable, or verification and delivery cannot fit. Preserve unsuccessful evidence and do not spend the full intended synthesis budget on local search.

Treat model interaction rounds as a budget as well as EDA time. Batch independent source reads and planned experiments, and use the executor's bounded wait for a persistent job instead of repeated short polls. If remaining interaction capacity is available, track it. Begin closing with enough rounds left for the functional result, final comparison and delivery; do not open another hypothesis during that reserve. If evidence cannot be completed, hand off the actual partial evidence and keep the original RTL. An optional scheduler may expose a verified handoff action; use it after the finalizing job succeeds to commit the exact bundle and end the actor. Without that integration, publish the ordinary artifacts and end with a concise report.

## Produce and test candidates

Create an overlay in the run directory and seal it with `variant`. Preserve interfaces, cycle behavior, signedness, widths, reset/enable/priority semantics and memory behavior. Compare a useful alternative such as unchanged replication, partial grouping or shared operation only when supported by the hypothesis. Do not universally force sharing or introduce latency changes to buy local speed.

A regional candidate can jointly add/remove modules, modify their callers and update declared source filelists. Freeze and test the complete candidate, including each version's ordered build inputs. Internal state representation and module boundaries may change while the agreed regional boundary behavior stays cycle-equivalent. Moving logic into a module is not itself an architecture revision. Changes to committed latency, parallelism, handshake, numerical behavior or storage/resource budgets require an explicit contract revision; publish that proposal and its evidence for the caller's architecture process instead of silently adopting it. No external architecture skill is required to investigate or deliver the proposal.

Run baseline and variant with the same tool, stage, defines, parameters and budgets. Use persistent job IDs, inspect `status` after disconnects, and never resubmit a lost worker as a resume. Timeout kills only the experiment's recorded process group. A lost worker can leave an orphan; status reports it without killing it or automatically launching another job.

Once baseline affordability is established, prefer `batch` for a finite preplanned group of still-needed measurements and paired checks. Its inline configurations and persistent IDs remove per-experiment submit/status/read loops. Plan the final comparison job lists and put optional `finalize` in the last group so successful evidence is handed off without another model turn. Explicit `reuse:true` may count a completed measurement with the exact source/tool/configuration request. Split groups to fit the external executor's deadline with setup, hashing and finalization margin; preserve the same measurement configuration across groups. `--tool-seconds` limits configured new-tool timeouts and remaining measured tool time, not the helper's full wall time. Read the command guide for the small plan schema.

An existing batch ID only observes the same frozen plan and receipts; it never resumes a disconnected claim or runs skipped jobs. A failed experiment stops later work, preserves actual outcomes and cannot become a successful measurement. `verify-batch` is read-only and returns a freshly checked ordinary finalization when one was produced. Inspect the compact batch outcome first; read individual logs when a job fails or evidence is incomplete.

For a scheduler that gives each command a disposable container, run the helper with `--foreground`, observe the scheduler's persistent outer job, and read the inner receipt only after that outer job finishes. Do not use inner PID status across container namespaces or duplicate an experiment while its outer owner remains active. Keep all generated outputs in the scheduler's writable scope. An outer exit code is transport/lifecycle evidence; inspect the inner outcome and source integrity separately. Per-job limits are not a total campaign cap; obey any caller-supplied campaign limits and preserve unfinished evidence when they are reached.

Budget inspection commands too when each scheduler submission consumes a job or timeout reservation. Prefer available read/list tools for source and log inspection, and batch independent cheap inspections when a helper command is necessary. Foreground experiments write their inner `result.json`, `tool.log` and execution artifacts directly; `worker.log` is a detached-launch log and may be absent.

Keep measurement and functional checks separate. Use built-in Yosys equivalence only for its supported scope, or run the project's real regression/equivalence program via `command`. Inspect the generated proof script, port coverage and raw logs. An exit code or caller-written pass flag is insufficient; command receipts require observed success markers and both candidate identities. Judge whether the actual tests cover the change. No markers can turn weak stimuli into a proof. Built-in equivalence rejects blackboxes and readmem designs; use the appropriate memory/macro-aware verification when needed.

Changed internal state names or hierarchy need not have a one-to-one correspondence. Choose verification that covers the region's reset, enables, priorities, cycle-visible outputs and affected callers. Full-chip formal proof is not mandatory for every candidate; a small helper proof alone is insufficient for a wider state/control rewrite. If suitable verification cannot complete within budget, retain a clearly unverified proposal and the remaining obligations. A later independent reviewer assesses the actual evidence and whole candidate, using the same ordinary RTL review interface when available.

Use repeated measurements for small timing differences and report variability. `compare` checks compatible identities and uses median improvement plus separated ranges. Its default is three observations per version and a 1.2 ratio; a smaller `--min-repeats` is allowed with a justified strategy. With few samples, state the limits on noise estimation and evidence strength; a single local result cannot establish full-design acceptance. Inspect resource statistics and runtime tradeoffs: faster lowering can still worsen full-design timing, mux/fanout cost or mapped area. State unmeasured effects explicitly.

Classify structural findings as `baseline_existing`, `candidate_new` or `unknown` using comparable check scope, configuration and actual issue signatures; equal warning counts alone do not establish attribution. Missing coverage or incomparable evidence remains unknown. Attach the source-bound health report to `compare`/`finalize` with `--health`; these commands freshly validate its evidence. Confirmed new structural problems prevent a recommendation to integrate. Existing or unresolved problems can accompany a scoped optimization proposal or an authorized synthesis-cost experiment, including time to a known failure boundary. They do not establish full-design readiness or acceptance. A report assembled after an experiment must not claim that a pre-experiment check occurred.

## Deliver

Output one of: a scoped candidate for integration, keep baseline, or evidence incomplete. Prefer a batch's planned `finalize`, or call `finalize` after collecting the measurement and functional job IDs: it runs the existing comparison and export checks and atomically publishes the patch, source/evidence identities and `finalization.json` together. Its repeated job arguments, ratio/repeat defaults and decisions match `compare`; it does not run EDA or weaken acceptance. Use a new delivery directory inside the standalone workspace, outside jobs/variants/batches. Repeating the exact invocation observes an already valid bundle without rewriting it; a conflicting or incomplete existing directory is rejected. Separate `compare`/`export` remain available.

Use `verify-finalization` for fresh read-only verification of that complete record and its actual receipts, sources and patch. Consumers can use its decision, reason, source/comparison identities and artifact paths without requiring a separate model-authored report. Negative outcomes retain their original decision and candidate-proposal status. Unverified or unsuccessful proposals keep the original RTL; they cannot be promoted by editing a JSON decision field.

Give a concise report with the hypothesis, selected scope, exact sources/top/configuration/tool, real commands/job IDs/log paths, measured time/memory/statistics, functional-check scope, candidate patch, decision and remaining uncertainties. Distinguish lexical observations, local lowering results, unmapped gate counts, mapped area, macro area and STA. State the next most valuable check; do not imply complete-chip acceptance from a local win.

For optional downstream integration, pass the exported patch, baseline/candidate identities, experiment scope, raw receipts and unresolved obligations as ordinary artifacts. Do not read another skill's private state or require its status vocabulary. A project may apply its normal implementation/review workflow after this standalone work is complete.

For a regional delivery also pass the whole file operation set and the baseline/candidate build identities. Modules, callers and filelists are one candidate; a consumer must not apply a convenient subset or mix an old caller with the new datapath. Independent review and any later full synthesis are separate caller decisions, not automatic side effects of a local comparison.
