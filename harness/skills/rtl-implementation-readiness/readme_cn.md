# RTL implementation readiness

这个模块放在初版 RTL 生成之后，解决需要真实工具小实验才能判断的问题：过程展开太慢、重复运算在不同阶段的复制与合并、存储器推断、选择逻辑深度，以及共享和复制的取舍。目标是缩短“发现问题—修改—验证—重新综合”的闭环，不承诺局部最优能得到全设计最优。

它可以单独使用。调用模型负责读代码、提出假设、编写候选；目录内 Python 标准库脚本负责冻结输入、分析线索、预算内执行、身份校验、比较和导出。无需另一个实现 skill、审阅 skill、微架构 skill、项目 adapter、外部模型命令服务或上级目录 runtime。需要时，把普通证据和补丁交给这些模块即可。

默认不修改用户源码，不自动启动大综合。每个实验从冻结树生成独立工作副本，记录工具、源码、参数、命令、日志和测量。重复提交同一作业身份只查询，不重跑；超时只清理自身实验进程组；失联不会自动“断点继续”。

既有文件内的 overlay 继续支持。需要围绕硬件职责边界重构时，可以显式选择区域工作区：新增或删除模块、修改调用者和候选的 source filelist，作为一个完整候选冻结、比较与导出。每个版本绑定自己的有序构建输入，原始文件与验证资产保持冻结；详见 [区域候选](references/regional.md)。小实验限制预算和问题范围，不限制改动行数或文件数。

区域边界的接口、周期、数值和架构资源承诺保持不变时，Readiness 可以自行提出并实现修改。若需要改变这些承诺，输出架构修订提案及证据交给调用方。诊断模式仍只读，优化模式才写隔离候选。区域级验证和受影响调用者回归需覆盖实际改变；函数级证明不能替代更大范围的状态/控制重构验收。

分析器是有范围的文本启发式，不能算出最终门数或精确耗时。比较看中位数改善及区间分离，默认每版三次；可说明理由后用 `--min-repeats` 选择更少重复。按选定策略只预留待补测量、配对功能检查和交付预算，复用经重验且源码/范围/配置/工具身份一致的已完成测量或 pilot。样本少时明确噪声估计和证据强度限制，单次局部结果不能代表全设计通过。共享的扇出、选择器、面积和时序代价仍需判断；证据不足时保留原版或给出证据不足。

深入追踪前，先用原始消息和源码位置对重要诊断做简要分组，按可能机制及源码区域保留不同问题；同一告警编号不代表同一原因。先识别哪些已有适用解释、哪些仍可能改变决策，再分配调查预算，未覆盖组及位置留给接续调查，避免把预算全部花在少数熟悉例子上。这不是逐条证明所有告警的要求。

取得工具诊断后，模型还负责调查会影响当前决策的重要发现：归并重复消息，回读相关源码、配置和上下游，给出有证据的原因解释，或说明仍待区分的假设及最小补充检查。告警数量、严重级别和退出码不能代替这项判断，也不要求逐条查完所有告警。优先复用已有证据，缺少适用 lint 或前端结构检查时在预算内补查；诊断模式只提出实验建议，获准的实验会话才执行。未覆盖或未完成的调查保持明确，局部检查通过不能关闭另一处疑点。具体项目、变量和代码组合不作为通用触发规则。

耗时实验前优先复用源码、构建配置、工具及检查范围适用的基线结构证据，在预算内补必要检查，修改后再对候选复查。只读 `health` 命令重验已有作业或外部证据，区分基线已有、候选新增及无法归因的问题；它不启动 EDA。未检查、超时或不完整的范围保持未知，事后整理报告不能倒推此前已完成检查。详见 [结构健康证据](references/structural-health.md)。

交付包含候选补丁、冻结身份、实际实验记录和结论。未验证提案仍可导出供讨论，但明确标成 proposal-only；它不是获准集成的候选。确定由候选新增的结构问题会使比较降为证据不足；基线已有或无法归因的问题可随局部提案交付，并继续开展获准的受控综合实验。结构问题未关闭时，不得宣称全设计结构健康、综合就绪或整体验收通过。推荐候选也只适用于测过的范围，不代表映射面积、顶层 STA 或物理实现通过。

独立 CLI 不依赖旧版 controller/observation/事务状态 API。固定文件工作区与历史证据保留原身份；新增区域工作区使用版本化身份，不原地改写旧记录。新项目可以直接调用 CLI，也可以用薄适配层把明确的源码、参数和命令传入。用法见 [SKILL.md](SKILL.md) 和 [commands.md](references/commands.md)。
